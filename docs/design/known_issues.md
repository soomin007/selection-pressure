# 알려진 함정 / 반복 금지 (Known Issues)

> 버그·설계 함정·작업 실수를 발견하면 여기에 "증상 → 원인 → 재발 방지책"으로 남긴다.
> 게임 버그뿐 아니라 프로세스 실수(도구 오용, 커밋 누락 등)도 포함.
> 세션 시작 루틴에서 이 파일을 먼저 읽어 같은 실수를 예방한다.

### sim 효과를 넣으면 관련 시각(부채꼴·도감·범례)도 반드시 함께 갱신 (일부만 고치면 어긋남)
- 증상: 수풀 시야 감소를 behavior(sim vision)에만 넣고, 화면 시야 부채꼴(worldView playerVision)과
  대백과 시야 그림에는 반영을 빼먹음. → 수풀 안에서 실제론 시야가 줄었는데 부채꼴은 그대로라 "수풀서
  잘 쫓아다닌다"로 보이고, 도감 그림도 부정확. 사용자 질책("수정할 때 빼먹지 말라").
- 원인: 한 효과(지형×형질)가 여러 표면(sim 계산·부채꼴 렌더·도감 SVG/설명·범례)에 걸쳐 있는데 sim만
  고침. 시야 부채꼴은 종 게놈 "고정값"이라 개체 위치(수풀)와 무관하게 그려지고 있었다.
- 재발 방지책: **새 sim 효과를 넣거나 형질/지형 계산을 바꿀 땐 그 효과가 보이는 모든 표면을 체크리스트로
  훑는다** — ① sim 계산 ② 그 값을 그리는 렌더(부채꼴·오라·틴트 등, "고정값"으로 계산하던 곳은 개체별로)
  ③ 대백과(SVG 그림 + 수치 + 설명) ④ 범례/HUD. 렌더가 sim 과 같은 함수를 쓰게 하면(behavior 의
  grassVisionFactor 를 worldView 도 import) 어긋남이 원천 차단된다(시각=로직 1:1의 실천).

### 이동체를 지형에 새로 구속시키면 길찾기도 함께 줘야 한다 (안 그러면 코앞에서 영영 못 잡는다)
- 증상: 땅 보스가 물·산을 못 넘게 막았더니(층위 도입), 보스가 먹잇감을 20~30px 앞에 두고도 끝까지 못
  잡았다. 화면상 계속 "움직이고는 있어서"(600틱 내내 이동) 멈춘 걸로도 안 보였다. 테스트 1건("추격자는
  보스 사망으로 집계된다")이 0 kill 로 실패해서야 드러났다.
- 원인: 이동을 "목표 방향으로 직진 + 축 분리 슬라이딩"으로만 두면, 물가·산자락에서 벽을 따라 좌우로
  미끄러지기만 하고 목표에 못 간다(반응형 조향의 local minima). 이미 개체(behavior)에서 겪고 격자 BFS
  (`navTo`)로 해결한 문제인데, **보스는 원래 지형을 무시하고 다녔기 때문에** 그 교훈이 안 옮겨져 있었다.
- 해결: `bossNavTo`(boss.ts) — 개체의 navTo 와 같은 구조(직선 보이면 직진 / 막히면 findPath 캐시 + funnel).
- 재발 방지책: **"이제부터 이 이동체는 지형에 막힌다"를 도입할 땐 같은 커밋에서 길찾기를 붙인다.** 통행
  판정(isPassable)만 추가하는 것은 절반짜리다. 진단 팁: "움직이는가"가 아니라 **"목표까지의 거리가 줄어드는가"**
  를 재라 — 벽을 따라 미끄러지는 것도 "움직임"이라, 이동량만 보면 정상으로 보인다(avoidWalls 때와 같은 맹점).

### 형질 카운터를 "절대 개체수"로 재면 비생존 빌드를 위협 탓으로 오독한다
- 증상: 새 보스(큰수리)의 시야 카운터를 재는데 "시야10 → 개체수 0.2 / 시야90 → 6.5" 라 카운터가 잘 듣는
  줄 알았다. 그런데 시야90 이 시야50(11.3)보다 **낮았다** — 카운터가 뒤집힌 것처럼 보였다.
- 원인: **보스 없는 기준선을 안 쟀다.** 실제로는 시야10 이 보스가 없어도 개체수 0.3(0/8 통과)인 비생존
  빌드였고(먹이를 못 찾아 굶는다), 시야90 도 기준선이 시야50 보다 낮았다(12.5 vs 15.3). 즉 그 숫자들은
  보스와 거의 무관했다. 게다가 도망 반경(visionFlee)을 90 까지 키우면 시야 큰 종이 내내 달아나느라 못 먹고
  굶는다(공황 아사) → 카운터를 세게 만들수록 오히려 뒤집히는 구간이 있다(60 이 최적).
- 재발 방지책: 카운터 형질을 잴 땐 **반드시 "그 위협이 없을 때"의 기준선과 함께 재고, 차이(위협의 영향)로
  판단한다.** 절대 개체수는 그 형질 자체의 생존력에 지배당한다. 그리고 회피 파라미터(도망 반경 등)는 키울수록
  좋은 게 아니다 — 채집 시간을 갉아먹는 지점이 있으니 값을 쓸어 보고 최적점을 찾을 것.

### 레이드 카운터 격퇴 점수를 무리 크기(합)로 재면 큰 무리가 거저 이긴다 — 평균으로 재라
- 증상(예방): 레이드 2단계에서 "무리가 카운터 형질을 시연하면 매 틱 격퇴 체력을 깎는다"를 만들 때, 처음엔
  huntable 무리 전체의 형질 충족도 **합**으로 재려 했다. 그러면 형질이 낮아도 무리가 크면(고성장 런) 합이 커져
  격퇴가 되고, 시대가 올라 무리가 커질수록 거저 이긴다(1단계 약탈자도 "diffMul 2 에서 6/6 은 무리가 커서"였다).
- 원인: 절대량(합)은 형질의 세기와 무리 크기를 뒤섞는다. 카운터는 "이 형질을 키웠는가"를 물어야 하는데
  합은 "무리가 큰가"에 지배당한다(known_issues 의 "카운터를 절대 개체수로 재면 오독" 과 같은 함정).
- 재발 방지책: 카운터 충족도는 **평균**(mean trait01)으로 잰다 — 무리 크기와 무관해 형질을 실제로 키운
  무리만 제 시간에 격퇴한다. 미스매치(형질이 floor 이하)는 충족도 **정확히 0** 이라 잘못된 빌드가 새지
  않는다(프로브: 느린 무리 vs 추격자 0/6, hp 97% 남음). rate 를 올려도 floor 아래는 0 이라 안전.

### 격퇴가 무리를 솎는 보스에 "수 압도" 계수를 걸면 자멸한다 (번식 카운터의 함정)
- 증상: 번식 카운터(사나운 무리=swarm)를 "다산 무리가 수로 압도해 격퇴"로 만들며 충족도에 무리 수 계수
  (`clamp01(n / 목표수)`)를 곱했더니 격퇴가 1/6 로 무너졌다(다산 빌드인데도). swarm 은 닿으면 무조건 솎아
  무리가 6~11 로 줄어드는데, 바로 그 줄어든 수가 계수를 깎아 격퇴가 더 느려지는 악순환.
- 원인: 카운터 보스가 그 카운터의 재료(무리 수)를 **직접 줄인다**. "수로 이겨라"인데 보스가 수를 없애니
  닭-달걀. diffMul 이 오르면(maxHp↑) 완전히 불가능해진다(0/6).
- 재발 방지책: 카운터 점수의 재료를 그 보스가 깎는 것이면 그 재료로 게이팅하지 말 것. 번식은 **평균 번식력**
  으로만 재고 수 계수를 뺐다(살아남은 소수가 빠르게 번식해 메운다) → 6/6→5/6→4/6(diffMul 1/1.22/2)로 회복.

### 레이드 wear 를 diffMul 로 안 키우면 시대가 오를수록 격퇴가 어려워진다(의도적, 단 한계 주의)
- 관찰: 격퇴 체력 maxHp 는 diffMul(시대)로 커지는데 매 틱 wear 는 안 키웠다 → 격퇴 시간이 시대마다 늘어
  높은 시대일수록 어렵다(무리·번식 카운터는 diffMul 2 에서 3~4/6). 이는 "시대가 지날수록 어려워진다"에 맞다.
- 주의: 후반 시대에 격퇴가 사실상 불가능해지면 그 카운터는 죽은 기능이 된다. 폰 체감 후 너무 빡세면
  raidWearRate 를 올리거나 wear 에도 diffMul 을 곱해(둘 다 스케일 → 격퇴 시간 시대 무관) 균형을 잡는다.

### sim 끼리 순환 import 는 함수 안에서만 쓰면 안전하다 (boss ↔ behavior)
- 상황: 레이드 격퇴가 무리 방어 판정(`herdShielded`, behavior.ts)을 읽어야 하는데 behavior 는 이미 boss 를
  import 한다(bossCanHunt 등). boss 가 behavior 를 import 하면 순환이 된다.
- 판단: **둘 다 import 를 함수 본문에서만 쓰면**(모듈 로드 시점엔 서로를 안 호출) ESM 라이브 바인딩으로
  안전하다(tsc·vite 통과, 스모크 통과). 방패 판정을 render·격퇴가 **같은 소스**로 읽어 시각=로직 1:1 을
  지키는 게 중복 구현(드리프트 위험)보다 낫다.
- 재발 방지책: sim 모듈 간 상호 참조가 필요하면 값을 최상위에서 쓰지 말고 함수 안에서만 호출한다. 최상위
  실행(상수 초기화 등)에서 상대 모듈 함수를 부르면 로드 순서에 따라 undefined 가 될 수 있으니 피한다.

### 형질을 값형질↔능력형으로 재분류하면 그 형질을 그리던 모든 화면을 함께 옮겨야 한다
- 증상: 드래프트 "내 종" 패널에서 무리 성향이 "강함 ~~+12~~ +8"처럼 **낱말(강함)에 숫자 델타(+12→+8)가
  뒤섞여** 보였다(사용자 지적). 카드 칩은 "무리 성향 강화"로 맞게 나오는데 패널만 어긋났다.
- 원인: v7 에서 무리 성향(herding)을 값형질 → 능력형(없음/보통/강함)으로 옮기며 `ABILITY_KEYS`·`traitWord`·
  카드 칩(cardEffectChips)은 고쳤는데, **draftPanel 의 `STAT_KEYS`(막대+숫자 델타 섹션)에 herding 이 그대로
  남아** 값은 낱말로(traitWord), 델타는 숫자로(cardDelta) 붙였다. 한 형질의 표시가 여러 화면에 흩어져 있는데
  일부만 옮긴 것 — "sim 효과를 넣으면 관련 시각도 다 갱신" 함정의 표시 버전. 같은 이유로 은신(camouflage)은
  드래프트 패널에 **아예 안 떴다**(값 섹션에도 능력 섹션에도 없었다).
- 재발 방지책: 형질을 값형질↔능력형↔중립으로 **재분류할 땐 그 형질을 그리는 모든 화면을 체크리스트로 훑는다**
  — ① traitWord/abilityLevel(공통) ② 카드 칩(cardEffectChips) ③ draftPanel STAT_KEYS(막대+숫자) vs 능력
  섹션(낱말+강화/약화) ④ buildPanel ⑤ 개체 카드 ⑥ 대백과. 능력형은 낱말(강함)+낱말 델타(강화)로 통일하고,
  값형질만 숫자+숫자 델타. 한 형질이 두 섹션에 걸치지 않게 한다(걸치면 낱말+숫자가 뒤섞인다).

### flex-wrap 컨테이너에 flex:none 을 주면 좁은 화면에서 wrap 이 안 돼 내용이 박스 밖으로 삐져나간다
- 증상: 효과가 4개인 카드(「정점의 포식자」: 공격·속도·시야·번식)가 좁은 폰(≈360px)에서 4번째 칩이 카드
  오른쪽 밖으로 삐져나갔다(사용자 지적). 취소선(감쇠 표시)까지 붙어 칩이 길어질 때 더 심했다.
- 원인: `.draft-chips { display:flex; flex-wrap:wrap; flex:none; }` — `flex:none`(= flex:0 0 auto)이라
  컨테이너가 **max-content 폭**(모든 칩이 한 줄)을 갖는다. 폭 제약이 없으니 flex-wrap 이 있어도 wrap 이
  트리거되지 않고, 부모(카드) 폭을 넘겨 오버플로. 넓은 폰에선 우연히 한 줄에 맞아 안 보이다가 좁은 폰에서 터진다.
- 재발 방지책: wrap 을 기대하는 flex 컨테이너에는 폭 상한을 **명시**한다 — `max-width:100%`(또는 `flex:1 1 100%`).
  그래야 컨테이너가 부모 폭에 갇혀 내부 flex-wrap 이 실제로 줄바꿈한다. `flex:none`+`flex-wrap` 은 모순이다
  (안 줄이겠다면서 줄바꾸겠다는 것). 검증은 **좁은 폭(≤360px)** 뷰포트 스크린샷으로 — 넓은 폰만 보면 못 잡는다.

### 통과기준 미달 패배도 "멸종"이라 부른다 — 1~2마리 살아있는데 멸종 표시(용어 불일치)
- 증상: 내 종이 멸종한 줄 알았는데 HUD("내 종 N")에 1~2마리가 살아있게 보인다(사용자 지적).
- 원인: `playerPopulation`(isPlayer 카운트, 죽은 개체는 매 step 제거)은 **정직**하다 — HUD 도 멸종 판정도 같은
  값을 본다. 진짜 멸종(관전 중 pop===0)이면 HUD 도 0 이다. 그런데 `endRun` 은 **모든 패배를 "멸종"으로 기록**
  한다(game.ts): 보스/대멸종 **관문을 통과기준(3마리) 미달**로 실패하면 1~2마리가 살아있어도 런이 끝나고
  "멸종"이라 불린다. 즉 숫자는 맞고 **말이 틀렸다**(1~2 생존 = 멸종 아님, 관문 실패다).
- 재발 방지책(미적용 — 사용자 결정 대기): 통과기준 미달 패배와 진짜 멸종(pop 0)을 **말로 구분**한다. 예:
  pop>0 이면 "관문 실패 · N마리 남음"·"명맥이 끊길 뻔", pop===0 이면 "멸종". 게임 문구라 임의로 안 바꾸고
  사용자와 합의해 정한다(CLAUDE.md 톤 규칙).

### 한쪽만 고정한 전체화면 오버레이는 내용이 길어지면 반대쪽(닫기 버튼)이 화면 밖으로 밀린다
- 증상: 후반에 형질이 많이 쌓이면 "내 종" 팝업이 화면 위로 자라, 헤더의 **닫기 버튼이 화면 밖으로** 밀려 못
  눌렀다. 사용자가 뒤로가기로 닫다 **게임 진행이 통째로 날아갔다**(SPA 라 뒤로가기 = 페이지 이탈).
- 원인: `.draft-popup-wrap` 이 `position:fixed; bottom:10px`(아래만 고정) + `.draft-popup` 높이 무제한.
  내용이 길면 팝업이 위로 무한정 자라 top 이 뷰포트 위로 넘어가고, top 에 있는 닫기가 화면 밖으로 나간다.
- 재발 방지책: 전체화면 오버레이/시트는 **뷰포트에 가둔다** — `max-height: calc(100dvh - N)` + `overflow-y:auto`.
  닫기/확인처럼 늘 눌러야 하는 컨트롤은 스크롤과 무관하게 보이도록 `position:sticky; top:0`(불투명 배경으로
  스크롤 내용을 가림). dvh 로 모바일 주소창까지 반영. 검증은 **짧은 뷰포트 + 내용 최대치**로 — 닫기의
  boundingClientRect 가 화면 안(inView)인지 스크롤 끝에서 확인(넓은/짧은 화면 둘 다 보면 결정적).
- 남은 개선(후속): 뒤로가기로 진행이 날아가는 것 자체를 막으려면 팝업 열 때 history state 를 push 하고
  popstate 로 팝업만 닫는 패턴이 필요하다(이번엔 닫기를 늘 보이게 해 우회).

### 예고를 "그때그때 다시 계산"하면 그 선택 때문에 예고가 거짓말이 된다 (얼려서 들고 있어야 한다)
- 증상: 시대 보상 드래프트가 "다음 시험: 사냥 5회"라고 예고했는데 실제로는 「먹이 45회」가 걸렸다.
  시드 40개 x 프리셋 4종으로 재면 640건 중 59건(9%) 불일치.
- 원인: 시험 선택이 `hash % 후보수`인데 **후보 목록을 그때의 게놈으로 매번 다시 만들었다.** 시대 보상
  카드는 x2 로 강화돼 식성이 사냥 문턱을 넘기기 쉽고, 그러면 후보가 3개에서 4개로 늘어 같은 해시가
  다른 시험을 고른다. 즉 **플레이어의 선택이 예고를 바꾼다** (예고를 보고 고른 건데).
- 재발 방지책: 예고한 값은 **그 순간 객체로 얼려 필드에 보관**하고, 실제 시작 시점은 재계산하지 말고
  그것을 채택한다(`pendingTrial`). 일반화: **"미리 보여주는 값"이 나중에 다시 계산되는 구조면 언제나
  거짓말이 될 수 있다.** 해시의 입력(후보 수 등)이 플레이어 행동으로 변하는지 반드시 따져 볼 것.

### 단일 슬롯 플래시 채널에 판정 문구를 실으면 다음 이벤트가 같은 프레임에 덮는다
- 증상: 라운드 시험 불합격 문구("사냥 1/2 · 불씨 하나가 꺼졌습니다")가 한 번도 화면에 안 나왔다.
  불씨 점만 말없이 하나 줄어든다. 채집 3회 중 2회가 보스로 이어지는 일정이라 절반이 그랬다.
- 원인: `highlights.flash` 는 Text 하나짜리 단일 슬롯이라 새 문구가 이전 것을 즉시 교체한다.
  `finishStage` 가 판정을 띄운 직후 같은 호출 안에서 `beginStage` 가 보스를 만들고, 같은 프레임 뒤쪽의
  이벤트 감지가 "보스 · ..." 로 덮어쓴 뒤에야 렌더된다. 사람이 볼 틈이 0프레임.
- 재발 방지책: 반드시 읽혀야 하는 문구는 **우선순위 슬롯 + 대기열**로 최소 표시 시간을 보장한다.
  일반화: **"띄웠다"와 "보였다"는 다르다.** 같은 프레임에 뒤따르는 이벤트가 있는지 보고, 있으면
  코드가 아니라 화면(스크린샷)으로 확인할 것.

### 공짜로 개체를 주는 장치는 새 판정 기준 전부에 새는지 확인해야 한다 (한 군데만 막으면 옆으로 샌다)
- 증상: 드래프트 스킵 보상 새끼(brood)가 "새끼 N마리" 시험에 안 세이도록 막아 뒀는데, **「무리 N마리」
  시험에는 그대로 들어갔다.** 스킵 한 번에 +2, 라운드에 레벨업이 두 번이면 +4. 스킵만으로 불합격을
  통째로 회피할 수 있었다(실측: 26 -> 28, 27 -> 29).
- 원인: 판정 기준이 둘(사건 계수기 / 개체 수)인데 구멍은 하나만 막았다. 계수기는 "세지 않기"로 막을 수
  있지만 개체 수는 세계의 상태라 "안 세기"가 불가능하다 -> 기준점 스냅샷을 떠서 빼야 한다.
- 재발 방지책: 보상으로 자원을 주는 장치를 넣거나 새 판정 기준을 만들 때 **그 장치가 모든 기준에
  어떻게 흘러드는지 하나씩 대 본다.** 개체 수처럼 "상태"를 읽는 기준은 시험 시작 시점의 스냅샷을 떠서
  차감하고, **표시(진행도)와 판정이 같은 식을 쓰게** 한다(따로 쓰면 화면이 거짓말한다).

### 기본값이 달린 뒤쪽 인자는 "안 넘겨도 컴파일이 통과해" 기능이 통째로 죽는다
- 증상: 2026-08-02 사용자 요구("남의 사건 연출이 정신사납다")로 넣은 야생 사건 다이어트가
  **한 번도 작동한 적이 없었다.** 야생끼리의 탄생·자연사 연출이 예전처럼 다 튀고 있었고,
  사용자는 그걸 "난잡하다"로 계속 느끼고 있었다(2026-08-03 발견).
- 원인: `effects.spawn(kind, x, y, tx?, ty?, mine = true)` 처럼 **핵심 플래그를 맨 뒤 기본값 인자로**
  뒀다. 호출부 `effects.spawn(ev.kind, ev.x, ev.y, ev.tx, ev.ty)` 가 `ev.mine` 을 안 넘겨도
  타입체크가 통과한다. sim 쪽 배관(world.emit 의 mine, effects 안의 dim 6곳)은 멀쩡히 살아 있는데
  값이 영영 기본값이라 `!mine` 분기가 한 번도 안 밟혔다. 테스트도 타입체크도 못 잡는다.
- 재발 방지책: **의미가 있는 플래그는 기본값을 주지 말고 필수 인자로** 두고, 그 값을 만들어 내는
  쪽(여기선 `world.emit`)과 **인자 순서를 똑같이** 맞춘다. 그래야 하나만 고쳐도 컴파일러가 나머지를
  잡는다. 일반화: "기능을 넣었는데 화면이 그대로"면 로직을 의심하기 전에 **그 값이 호출부에서 실제로
  건네지는지** 먼저 확인하라(기본값이 있으면 안 건네도 조용하다).

### 전체 화면 패널이 곧바로 뜨는 자리에서는 캔버스 플래시가 무조건 가려진다
- 증상: 레벨업 카드창을 라운드 경계로 옮겼더니, 바로 앞에 띄운 라운드 판정 플래시가 카드창(+블러 베일)에
  덮여 안 보이게 됐다. "왜 불씨가 하나 줄었는지" 알 길이 사라진다.
- 원인: 플래시는 Pixi 캔버스에 그리고 카드창은 그 위의 DOM 오버레이다. 표시 시간(2.2초)이 남아 있어도
  다음 프레임부터 가려진다. 앞선 함정("단일 슬롯 플래시를 다음 이벤트가 덮는다")과 같은 계열인데,
  이번엔 덮는 쪽이 같은 채널이 아니라 **다른 레이어**다.
- 재발 방지책: 어떤 사건 직후에 전체 화면 패널을 여는 흐름을 만들면, 그 사건의 문구를 **그 패널 안에도**
  실어라. 이번엔 카드창의 제목 자리를 판정이 차지하게 했고(원래 제목은 정보가 없는 문구였다),
  플래시와 제목이 **같은 함수(verdictLine)**를 쓰게 해 두 자리가 갈라질 수 없게 했다.

### 겹침 검사기는 "요소 상자"가 아니라 "글자 사각형"으로 재야 한다 (오탐이 검사기를 무력화한다)
- 증상: 검사 대상을 13개 화면으로 늘리자 겹침이 27건 쏟아졌는데, 실제 문제는 1건뿐이었다.
  나머지는 ① 대백과·내 종 팝업 같은 **전체 화면 오버레이가 뒤 화면을 덮은 것**(정상) ②
  가운데 정렬된 블록의 **상자가 줄 전체를 차지해** 글자는 안 닿는데 옆 버튼과 겹친 것으로 나온 경우.
- 원인: 요소의 `getBoundingClientRect` 는 글자가 실제로 칠해진 영역이 아니고, 겹친 두 요소 중
  무엇이 위에 있는지도 모른다. 오탐이 많으면 검사기를 안 보게 되어 진짜 사고를 놓친다.
- 재발 방지책: 텍스트 노드에 `Range` 를 걸어 **글자 줄 단위 사각형**을 쓰고, 각 사각형에 점을 찍어
  `elementFromPoint` 로 **그 픽셀에서 맨 위에 있는지** 확인한 뒤 가려진 글자는 후보에서 뺀다.
  히트 테스트 전에 `* { pointer-events: auto }` 를 주입해야 `pointer-events:none` 인 HUD 글씨가
  뒤 캔버스로 뚫려 오판되지 않는다. 캔버스에 그리는 UI(미니맵)는 앱이 `body.dataset` 에 표시 여부를
  남겨 검사기가 읽게 한다.

### 온보딩(첫 경험) 게이트를 "판 안의 진행도"로 걸면 숙련자가 매 판 초보 취급을 받는다
- 증상: "첫 판을 친절하게"를 구현하며 단순화 게이트를 `era === 0` 으로 걸었다. 그 결과 **백 판을 한
  사람도 매 런 첫 시대가** 종 셋짜리 평평한 초원 · 시험 없음 · 챔피언 없음이 됐다. 사용자 지적:
  "쓸데없이 첫 시대가 모두 버려지고 있어". 게다가 첫 시대(극단적 단순) → 둘째 시대(시험·불씨·챔피언·
  바이옴·대멸종·넓은 맵이 한꺼번에)로 **절벽**이 생겼다.
- 원인: 온보딩이 답해야 하는 질문은 "**이 사람이 이 게임을 얼마나 겪었는가**"인데, `era` 는 그게
  아니라 "지금 판이 얼마나 진행됐는가"다. 두 축을 같은 변수로 쓰면 판을 새로 시작할 때마다 경험이
  0 으로 리셋된다. 게다가 게이트가 불리언 하나(`simplified`)라 "전부 잠김 ↔ 전부 열림" 사이에
  중간이 없었고, 그 경계가 곧 절벽이 됐다.
- 재발 방지책: **온보딩 게이트의 입력은 반드시 판 밖에서 누적되는 값**(끝낸 런 수 같은 저장 값)이어야
  한다. 지금은 `onboardingStep(runsCompleted, era) = min(3, 끝낸 런 수 + 시대)` 하나가 단일 진실이다
  (`src/game/config.ts`). 그리고 **한 단계에 한 가지씩만 열어** 절벽을 계단으로 만든다 — 계약(단조
  증가·기능이 다시 안 닫힘)은 테스트로 못박고, 실제 계단 크기는 `npm run probe -- steps` 로 눈으로 본다.
  ⚠ 무엇이 언제 열리는지는 **화면에서 알아채게** 할 것(여기선 시대 보상 드래프트의 안내 한 줄).
  ⚠ 좁힌 세계를 만드는 인자의 **기본값은 늘 "온전한 세계"** 로 둔다 — 그래야 골든 지문과 기존 밸런스
  테스트가 그대로 살고, 새 옵션을 더할 때도 기존 세계가 안 흔들린다.

### 규칙이 여럿인 판정을 "주효과 하나"로 줄여 재면 샌다 (무의미 카드 필터)
- 증상: 정점을 넷(속도·시야·공격력·번식력) 찍고 무리 성향도 최대인 후반 게놈에서 「철벽 대형」
  (무리 22 · 공격 12 · 번식 -6)이 드래프트 후보로 떴다. 칩은 "무리 성향 이미 최대 · 공격력 이미 최대 ·
  번식력 정점 · 안 내려감" — **세 효과가 전부 무효인, 아무것도 안 바뀌는 카드가 선택지 한 칸을 차지**했다
  (2026-08-05 폰 실기. "안 바뀌는 카드는 내지 말라"는 이전 지시의 재발).
- 원인: `cardRedundant` 가 **주효과(가장 큰 양수 효과) 하나만** 보고 판정했다. 「철벽 대형」의 주효과는
  herding 인데 v7 에서 herding 이 능력형으로 재분류되며 판정 대상(`GROWTH_TRAITS`)에서 빠져 마지막
  `return false` 로 새어 나갔고, **나머지 두 효과가 막혔는지는 아예 안 봤다.** 게놈이 실제로 얼마나
  움직이는지를 정하는 규칙은 이미 여섯이다(성장 스케일 · 상한 근접 감쇠 · 정점 고정 · 희생 · 클램프 ·
  수영 뚜껑). 판정은 그 규칙들을 눈으로 옮겨 적은 **축약본**이라, 규칙이 하나 늘거나 형질이 재분류될
  때마다 새는 곳이 생겼다(같은 규칙을 두 곳에 적으면 갈라진다는 이 프로젝트의 단골 함정).
- 재발 방지책: **판정을 축약하지 말고 진짜 적용 함수를 돌려 결과로 재라.** `cardRedundant` 는 이제
  `cardGenomeDeltas`(게놈 사본에 `applyCard` → 전후 차이)로 판정한다 — 화면 표시(칩·스탯바)와 판정이
  **같은 함수**를 보므로 갈라질 수 없다. 남는 예외는 "게놈 숫자는 변하는데 sim 이 못 느끼는 자리"뿐이고
  (눈이 먼 종의 시야 · 문턱 넘은 수영 · 이미 열린 관문), 그것만 한 함수(`deltaGivesSomething`)에 근거가 되는
  sim 규칙과 함께 모았다. 일반화: **"이 선택이 의미가 있는가"를 묻는 판정은 그 선택을 실제로 해 보고
  답하게 한다.** 조건을 나열해 흉내 내면 조건이 늘 때마다 판정만 뒤처진다.
- 함께 지킬 것 둘:
  · **부분 무효는 남긴다** — 하나라도 실제로 바뀌면 정상 후보다(「듬직한 몸」: 시야는 최대여도 몸집은 오른다).
    전부 막힌 것만 뺀다. 다만 이득이 전부 막히고 **대가만 남은** 카드도 뺀다(눈이 먼 종의 「천리안」은
    시야가 죽은 값이라 걸음 -6 만 남는다).
  · **필터를 세게 만들 땐 후보 고갈을 실측한다** — 카드를 못 채우는 드래프트가 더 나쁜 결함이다.
    실측(2026-08-05): 정점4+무리100 에서 전제 통과 86장 → 49장으로 줄지만 갈래별 23~26장, 3600 뽑기 중
    3장 미달 0회. 전 형질 100 이라는 극단에서도 20장(갈래별 9~13)이 남는다.

### 판정이 안 보는 축에 배율을 곱하면 "난이도가 오른다"가 통째로 거짓말이 된다

- 증상: 위협 배율이 시대마다 복리로 올라 시대 5 에서 ×2.22 가 되는데, **시대 끝 개체 수는 22.9 → 22.7**
  이었다. 숙련자 탈락률도 시대 3 이후 27~29% 에 고정됐다. 화면에도 문서에도 "시대가 지날수록
  어려워진다"라 써 있는데 플레이어에게는 아무 일도 안 일어난 것이다.
- 원인: 배율이 곱해지는 곳(보스 격퇴 체력·즉사 반경·떼 수·대멸종 세기)이 **전부 관문 안**인데,
  관문 판정이 "1마리만 살아 있으면 통과"였다. 그래서 위협이 무리를 아무리 얇게 만들어도 판정
  결과가 안 바뀌었다. 배율은 성실히 커지고 있었지만 **결과에 닿는 경로가 없었다.**
- 재발 방지책: **난이도 손잡이를 만들 때 "이 값이 커지면 어떤 판정이 달라지는가"를 먼저 답하라.**
  답이 없으면 그 손잡이는 장식이다. 여기서는 둘을 함께 붙여 고쳤다: ① 관문 판정 자체를 시대마다
  올리고(`passNeeded` · 1·2·3·4·6마리) ② 관문 **밖**의 하루하루에도 배율이 닿게 했다
  (`eraPredatorPressure` · 사냥하는 야생의 수). 검증도 배율이 아니라 **시대 끝 개체 수·탈락률**로
  한다 — 배율 표를 보고 "올랐다"고 적은 것이 이 사고의 시작이었다.

### 상한 근접 감쇠의 지수를 올리면 천장 바로 아래에 "영영 못 넘는 벽"이 생긴다

- 증상: 정점 도달을 늦추려고 감쇠 지수를 0.5 → 0.85 로 올렸더니, 「날쌘 걸음」(+15)을 **30장 쌓아도
  속도가 99 에서 멈췄다.** 정점이 비싸진 게 아니라 **닫혔다.**
- 원인: 증가폭이 `Math.round` 로 정수화되는데, 99 에서 남은 여유가 2% 라 어떤 카드도 반올림하면
  0 이 된다. 감쇠가 곱셈이라 지수를 조금만 올려도 천장 근처에서 0.5 미만 구간이 통째로 생긴다.
  "점근하되 닿기 어렵다"고 적어 둔 곡선이 실제로는 "닿을 수 없다"였다.
- 재발 방지책: **곱셈 감쇠 + 정수 반올림을 쓰는 곳에는 바닥을 둔다** — 여기서는 "올리는 카드는
  적어도 1 은 올린다"(`effectiveDelta`). 표시도 같은 함수를 읽으므로 "+1"이라 뜨고 실제로 +1 이
  붙는다. 그리고 곡선을 만졌으면 **끝까지 쌓아 보는 테스트**로 도달 가능성을 못 박아라
  (`game.test.ts` 의 "정점까지 몇 장" 테스트) — 한 장의 증가폭만 보면 벽이 안 보인다.

### 시대마다 오르는 천장을 감쇠 분모에 그대로 넣으면 "정점 도달을 늦춘다"가 뒤집힌다

- 증상: 형질 천장을 시대마다 올리면서(100 → 118 → 139 → 164 → 194) 감쇠도 그 천장 기준으로
  쟀더니, 정점(100) 도달이 늦어지기는커녕 **더 빨라졌다**(시야 정점 도달 시대 2.7 → 2.5,
  도달한 런 16/32 → 24/32). 늦추라는 지시를 정확히 거스른 결과였다.
- 원인: 감쇠는 "천장까지 남은 여유"에 비례하는데, 천장이 194 로 올라가면 형질 95 에서의 여유가
  10%(천장 100 기준)에서 69%(천장 194 기준)로 뛴다. 즉 **천장을 올리는 행위 자체가 100 근처를
  헐겁게 만든다.** 성장을 열어 주는 손잡이와 정점을 늦추는 손잡이가 같은 식을 공유하고 있었다.
- 재발 방지책: 두 목적이 한 식에 얽히면 **구간을 갈라라.** 여기서는 100 아래에서는 "천장 100 기준
  여유"와 "이 시대 천장 기준 여유"의 기하평균을 쓰고, 100 위에서는 이 시대 천장만 본다
  (`growthFalloff`). 문턱은 늘 비싸고, 뚫으면 그 시대의 한계까지 다시 트인다. 일반화: **한 상수를
  올렸을 때 의도한 지표가 반대로 가는지 반드시 실측하라** — 곡선은 직관을 자주 배신한다.

### 디버그 문으로 만든 상태가 진짜 경로와 다르면, 그걸로 재는 검사기가 통째로 거짓말이 된다

- 증상: 겹침 검사기에 "관문 생존 칩(생존 21/6)이 붙은 목표 줄" 장면을 넣었는데 칩이 한 번도 안 떴다.
  검사기는 조용히 통과했을 것이고(칩이 없으면 겹칠 것도 없다), 나는 "잰 화면"이라 믿었을 것이다.
- 원인: `debugSummon` 이 **채집 라운드 한복판에 위협만 얹었다.** `stageIndex` 는 그대로라
  `currentKind()` 가 "forage" → `survivorsNeeded` 가 0(= 관문 없음)이었다. 그래서 화면은
  "위협: 그림자 매복자"라고 말하면서 동시에 "끝까지 살아남으면 통과합니다"라는 **거짓말**을 하고
  있었다. `?dev` 패널로 보스를 부른 사람은 늘 그 거짓말을 보고 있었던 셈이다.
- 재발 방지책: **디버그 소환·치트 문은 진짜 상태 전이를 그대로 밟게 만든다**(여기서는 `stageIndex` 를
  그 관문 자리로 옮긴다). 그리고 검사기 장면에는 **"그 UI 가 실제로 떴는지"를 확인하는 단언을 넣어라**
  (`.goal-follow` 에 "생존"이 들어있지 않으면 throw) — 안 넣으면 아무것도 안 재고도 초록불이 뜬다.
  이 저장소의 "띄웠다와 보였다는 다르다"의 검사기 버전이다.

### 모듈 수준 상태에 얹힌 값은 필드 대입이 아니라 전용 문으로 바꿔야 한다 (시대 ↔ 형질 천장)

- 증상: 후반 시대 화면을 만들려고 `game.era = 4` 를 대입했더니, 생존 기준·포식 압력은 4시대 값이
  되는데 **드래프트 막대의 눈금만 첫 시대(천장 100)** 였다. 화면 절반은 4시대, 절반은 1시대.
- 원인: 형질 천장은 `genome.ts` 의 모듈 수준 상태(`activeCeiling`)이고, `era` 필드는 그걸 안 건드린다.
  둘을 잇는 것은 `applyEraCeilings()` 뿐인데 그건 private 이라 밖에서 부를 수 없었다.
- 재발 방지책: **"이 값을 바꾸면 반드시 함께 갱신돼야 하는 것"이 있으면 필드 대입을 열어 두지 말고
  전용 문(`debugSetEra`)만 두고 거기서 함께 갱신한다.** 대입은 조용히 절반만 바꾼다. 일반화: 모듈
  수준 상태(싱글턴)를 쓰는 값은 그 상태를 세팅하는 입구를 **하나로** 묶어라 — 입구가 늘 때마다
  "여기서도 불러야 하는데 안 불렀다"가 생긴다(1단계에서도 새 런·다음 시대·로비 복귀 셋을 세어야 했다).

### 종 다양성: 단일 먹이 자원에서 경쟁 배제로 금방 1~2종만 남음
- 증상: 야생종을 늘려도(3→6종) 수천 틱이면 1~2종(보통 내 종)만 남음. 시드 편차 큼.

- 완화책(현재): 생존 전략 분리(다산/저대사 장수/잡식/포식) + 야생 영역(클러스터) 스폰으로
  초·중반 공존을 늘림. 후반 붕괴는 못 막음.
- 근본 해결(적용 478e1d1): (1) 먹이 종류 분할 — food.kind 3종, 야생 초식종마다 다른 종류 전문이라

### 월드 스케일(areaScale) 도입 시 절대 상수를 빠뜨리면 그 축에서 분포가 붕괴
- 증상: 맵 3배(areaScale 9) 후 내 종은 늘고 야생만 단조 급감(t2000 야생 4%). 작은 월드(scale 1)는
  야생이 회복 진동(46%)하는데 큰 월드만 회복 못 함.
- 원인: areaScale 로 개체·먹이·cap·통과기준은 면적 비례시켰지만 **두 절대 상수를 빠뜨림** —
  ① 야생 보금자리 spread(72px): 큰 맵에서 좁은 점에 과밀 → 국소 먹이 소진 후 집단 아사.
  ② 이주 floor 4·batch 3: 큰 맵 종당 ~90 대비 4%라 보충이 무의미 → 줄어도 회복 못 함.
- 해결(4f0a45a): spread = 72·sqrt(areaScale)(길이라 제곱근), 이주 floor·batch = ×areaScale.
  큰 월드 야생 t2000 4%→48%(내 종과 균형).
- 재발 방지책: **월드 크기/스케일을 바꿀 땐 "모든" 절대 상수를 면적 기준으로 점검하라** — 개체수·
  먹이수·cap·통과기준(면적 비례) / 보금자리·이동거리 같은 "길이"(제곱근 비례) / 이주 바닥·보충량.
  하나만 절대값으로 남으면 그 축에서만 밀도가 어긋나 분포가 한쪽으로 쏠린다. 작은 vs 큰 월드 같은
  지표를 A/B 로 재서 "큰 월드만의 이상"을 가르는 게 진단의 핵심(원래 그런 것 vs 스케일 버그).

### 반응형 벽 회피(avoidWalls)는 진동을 만든다 — headless 프로브가 진동을 못 잡아 폰과 어긋남
- 증상: 이동 차단(지형) 후 생물이 벽에 막히면 못 돌아감. `avoidWalls`(가려는 방향이 막히면 desired 를
  통행 방향으로 회전)를 넣었더니 폰에서 끼임이 **오히려 더 늘었다**(사용자). 그런데 headless
  프로브("변위<0.1=정지")로는 끼임이 줄어든 것으로 측정돼 정반대 결론이 나왔다.
- 원인: ① avoidWalls 가 매 틱 좌우(±0.35rad)를 독립 탐색 → 벽 옆에서 선택 방향이 휙휙 뒤집혀
  desired 가 좌우로 진동 → 제자리 맴돌기. ② 반응형 조향은 오목 지형·막다른 만에서 local minima 에
  빠져 못 빠져나옴(근본 한계). ③ 프로브가 "정지"만 재서 **진동(변위는 있음)을 "안 끼임"으로 분류** —
  떨림 사건과 똑같은 맹점.
- 해결(7d653d7): 타일 격자 BFS 길찾기로 교체(`terrain.lineOfSight` 직진 우선 + 막히면 `findPath`
  경로 추종 + funnel 단축, 경로는 entity 캐시). desired 방향을 흔드는 게 아니라 "어디로 갈지"를
  격자에서 풀어 진동·local minima 가 없다. cohesion 도 무게중심이 벽 너머면 끔.
- 재발 방지책: **시각 현상(떨림/진동/맴돌기)을 "정지" 같은 단일 지표로 판단하지 말 것.** 프로브에
  방향 반전율(벽 옆 변위가 한 틱 전과 거꾸로) 같은 진동 지표를 함께 재고, 최종 판단은 폰 눈.
  정적 장애물(지형) 회피에 반응형 조향은 부적합 — 격자 길찾기가 정답.

### 우호 친척 종을 내 종 "근처"에 스폰하면 소수 밸런스가 깨진다 (근처 동거 불가)
- 증상: 친척 종(우호)을 내 종 보금자리 근처에 두려 하니(옆 동네 offset·먹이 분리·수↓ 다 시도),
  Phase 5 통과기준 테스트가 반복 실패 — 특히 외톨이 사냥꾼·그림자 매복자 보스에서 내 종이 0~2로
  전멸(통과기준 3 미만). 세션 2·3 두 번 프로브로 재현.
- 원인: ① **무리 cohesion 이 종 무관 이웃(grid.neighborhood COM)** — 친척이 내 종 무리에 섞이면
  COM 에 친척이 포함돼 내 종 뭉침이 흐트러진다. 외톨이/매복 보스는 "뭉치면 생존"이라 결속이 깨지면
  치명적. ② 소수 개체 + 통과기준 3(빡빡한 마진)이라 국소 먹이를 조금만 함께 먹어도 hi 가 3 미만.
  offset·먹이 분리(foodKinds)·수↓로도 "섞이면" ①이 남아 근본 해결 안 됨.
- 해결(채택): **친척은 맵의 독립 영역에 스폰**(야생종처럼). 떨어져 살되 이동하다 만나면 friendly 라
  서로 사냥·도망 안 해 자연스레 섞인다(스포어식 우호). 근처 동거 콘셉트는 버림.
- 재발 방지책: 소수 개체 게임에서 **새 종을 내 종과 같은 자리에 두지 말 것.** cohesion 이 종 무관이라
  무리가 섞여 결속·먹이가 교란된다. "같이 사는 느낌"은 독립 스폰 + 이동 중 조우(friendly)로 충분.
  근처 동거를 살리려면 cohesion 을 같은 종(+우호)만 보게 바꿔야 하는데, 그건 무리 역학 전면 재튠이라
  비용이 크다(현재 안 함).

### 형질 스케일을 정수화(0~100 반올림)하면 야생종 형질이 미세 달라져 밸런스가 이동한다
- 증상: 형질을 0~1 소수 → 0~100 자연수로 전환(값 ×100, 계산은 ÷100 정규화라 수학적 동일). 내 종

- 원인: randomGenome·야생 드리프트가 형질을 반올림(clampTrait)하면서 야생종 형질이 스케일 전과
  미세하게 달라졌다 → 야생 생태(먹이 경쟁)가 변동 → 내 종 개체수가 통과기준 경계에서 이동. 아슬한
  케이스(약탈자 lo·매복자)가 그 노이즈로 넘어갔다. 계산은 동일해도 "입력값의 이산화"가 sim 을 흔든다.
- 재발 방지책: 스케일/정수화처럼 형질 표현을 바꿀 땐 밸런스가 "수학적으로 동일"이라도 이산화로
  분포가 이동할 수 있다 → 통과기준 테스트를 프로브로 재확인하고, 개체 시뮬 + 소수 개체라 단일 시드
  형질 게이트가 원래 아슬한 시련은 "카운터 방향(hi>lo)·kill 발생"으로 견고화(엄격한 lo<기준은 노이즈).

### HUD 고정 위치 요소는 "가변 길이 텍스트"와 같은 줄에 두지 말 것 (우측 고정 위젯↔긴 라벨 겹침)
- 증상: 정보 박스 둘째 줄(상태) 우측에 낮밤 타이머(노란 점+라벨)를 고정했는데, 상태 첫 줄이

- 원인: 좌측 텍스트는 내용에 따라 가로로 늘고, 우측 위젯은 절대 좌표 고정. 같은 y(줄)에 두면

  내렸는데, 이후 그 둘째 줄에 긴 라벨(단계·시련 이름)이 들어오며 반대로 겹쳤다.
- 해결(aff577a): 타이머를 "짧고 안정적인" 줄(개체 수 = 소수 개체라 짧음) 우측으로 옮겨 세로
  분리 + 상태 첫 줄에서 "단계 N/M ·" 프리픽스 제거(타임라인 막대가 대신 보여줘 중복).
- 재발 방지책: 우측 고정 위젯은 **그 줄의 좌측 텍스트가 최대로 길어져도 안 닿는지**로 자리를
  정한다. 길이가 가변인 텍스트(단계·종·시련 이름 등) 줄에는 고정 위젯을 얹지 말고, 길이가
  거의 일정한 줄(개체 수)이나 별도 영역에 둔다. 좌표로 "좌측 끝 x < 위젯 시작 x"를 계산해 마진 확인.

### 시각(이펙트)은 실제 로직과 반드시 1:1 로 일치시킨다 (전역 로직을 국소 이펙트로 그리지 말 것)
- 증상: 보스 6종 중 5종(독안개·사나운 무리·약탈자·외톨이 사냥꾼·그림자 매복자)이 **전역 솎기/흡수**
  (위치 무관, 매 틱 모든 개체를 확률로 솎음)인데, 시각은 "떼(작은 점 뭉치)"·보스 점을 특정 위치에
  그려 놨다. → "저기 떼가 있는데 왜 여기 있는 내 애가 죽지?" 로직과 이펙트가 따로 놀아 사용자가 혼란·불신.
- 원인: 로직(전역)과 시각(국소 개체)을 각각 만들고 맞추지 않음. 개체가 없는 현상(전역 재난)에 개체(점)를
  그렸다. 게다가 "보스"라는 한 이름에 개체형(추격자)과 전역 재난(독안개)을 섞어 불러 더 헷갈림.
- 재발 방지책(원칙): **새 메커니즘을 만들 때 시각을 로직과 1:1 로 설계한다.**
  · 전역 효과(위치 무관) → 화면 전체 표현(전체 틴트/맥동, 사방에서 벌어지는 kill 이펙트). 개체(점) 금지.
  · 국소 효과(특정 위치) → 그 위치에만 표현.
  · 개체가 실제로 존재하는 것만 개체로 그린다(추격자=점+즉사 반경, 도망 대상).
  · 이름도 로직에 맞춘다: 실제 개체=보스, 전역 재난=시련. "무엇이 어떻게 죽이는지"가 화면과 말에서
    일치해야 "왜 졌는지"를 안다(기획서 §7 가독성). 로직을 먼저 정하고 시각·용어를 거기에 맞춘다.

### 새 통행/감각 파라미터(canFly 등)를 배선할 때 "기존 기본값에 의존하던 호출"을 바꾸면 밸런스가 이동한다
- 증상: 날개(비행) 형질로 terrain 통행 함수에 `canFly` 파라미터를 추가하며, cohesion 판정의
  `lineOfSight` 호출도 `(…, canSwim)` → `(…, canSwim, canLand, canFly)`로 "더 정확하게" 바꿨다.
  그랬더니 내 종/야생이 날개 0(비행 안 함)인데도 독안개 통과기준 테스트가 경계에서 실패(lo=base=1).
  고산 먹이(독립 rng)를 0으로 꺼도 실패해 "고산 먹이가 원인이 아님"이 드러났다.
- 원인: 그 `lineOfSight` 호출은 원래 `canLand`를 **생략(기본값 true)**했다. `canLand`를 명시하니 물
  전용 종(swimming≥90, 물고기 떼)의 `canLand`가 false가 돼 cohesion 판정이 바뀌고(육지 너머 무리를 안
  봄), 다종 생태의 궤적이 이동 → 내 종 개체수가 경계에서 넘나들었다. 날개와 무관한 "물 전용 종 동작
  변화"가 진짜 원인.
- 재발 방지책: 새 통행/감각 파라미터를 배선할 때 **"기존에 기본값에 의존하던 호출"은 그 기본값을 유지한
  채 최소로만 바꾼다.** 정확성을 위해 인자를 더 넘기고 싶어도, 그 인자가 특정 종(물 전용 등)에서 기존과
  다른 값이면 밸런스가 이동한다. 밸런스와 무관한 부수 판정(cohesion 등)은 원래 호출을 보존하는 게 안전.
  진단 팁: **새 자원(고산 먹이 등)을 의심하기 전에 그 자원을 0으로 꺼 원인을 빠르게 가른다**(끄고도
  실패하면 그 자원이 원인이 아니다).

### 친척(우호 종)이 플레이어 능력치까지 닮으면 극단 게놈 통과기준이 흔들린다
- 증상: 친척을 시작 프리셋에 맞춰 닮게 하려고 친척 게놈을 플레이어 기반으로 블렌드(follow 0.55)했더니
  metabolism 90 같은 극단 게놈으로 통과기준을 재는 밸런스 테스트(한파 고대사 통과)가 실패. follow 를
  0.4 로 낮추자 오히려 저대사 테스트까지 겹쳐 3개로 늘었다(값 하나로 모든 극단을 못 맞춤).
- 원인: 친척이 플레이어 능력치(특히 대사)를 따라가면 극단 플레이어와 같은 환경 압력을 함께 버텨
  과경쟁 → 내 종 통과 개체수가 경계에서 떨어진다. follow 를 조절해도 고대사/저대사 극단마다 경쟁
  구도가 반대로 움직여 단일 값으로 수렴 불가.
- 해결: **능력치(속도·공격·시야·무리·대사·번식)는 플레이어와 독립(기존 50±10)으로 두고**, "친척다움"은
  이동 방식(수영·날개·초음파)과 식성 방향으로만 표현. 능력치가 플레이어 무관이면 극단 게놈에서도 친척
  경쟁이 불변 → 통과기준 보존(91 테스트 통과). 이동/감각/식성만 반영해도 "갈라진 친척" 느낌은 충분.
- 재발 방지책: 우호/경쟁 종을 플레이어 형질에 연동할 땐 **환경 적합도에 직접 걸리는 능력치(대사 등)를
  연동하지 말 것.** 정체성 형질(이동·감각·식성)만 연동하면 통과기준 밸런스를 안 건드린다.

### 소수 개체 + "닿으면 즉사 판정" 사냥에선 순수 DoT(지속 피해)·전투 형질이 개체수에 잘 안 드러난다
- 증상: 독침(venom)을 "물면 독 걸려 지속 피해(DoT)로 죽는다"로 구현했으나 프로브에서 중독사가 0, venom
  유무가 자생 개체수를 거의 안 바꿨다(venom100 atk10 ≈ venom0 atk10). 순수 DoT(즉사 안 함)로 하면 venom
  종이 사냥 완료를 못 해(무한 추격) 굶어 멸종.
- 원인: ① 사냥이 "사거리 안 매 틱 즉사 확률 판정"이라 즉사(killChanceBias 0.5 지배적)가 DoT 축적보다 먼저
  죽여 독이 쓰일 틈이 없다. ② 개체수는 채집+번식이 주 결정요인이라 사냥 효율 차이가 개체수로 잘 안 번진다
  (attack 조차 atk10→60 에서 자생 5→9로 완만). ③ 소수 개체+단일 시드는 노이즈 큼.
- 해결/타협: 독을 "즉사 확률에 누적 기여(poison/100 × venomKillBonus)"로 재설계 — venom 종은 여러 번 물어
  독 쌓아 약해진 먹이를 잡는다(attack=즉발 / venom=누적 트레이드오프). DoT 는 약하게 유지(도망친 먹이
  마무리) + 독 걸린 개체 보라 tint(지속 피해 시각 피드백). 순수 중독사는 포기.
- 재발 방지책: 소수 개체 게임의 새 전투 형질은 "개체수 우위"보다 **명확한 메커니즘 차이 + 시각 피드백**을
  노려라. 순수 시간축 효과(DoT)는 즉사 판정 사냥과 충돌하고 관찰도 어렵다. 테스트도 "개체수 우위"(노이즈)
  대신 "메커니즘 작동"(독이 걸린다·자생·사냥 발생)으로 견고히. 밸런스 세부는 폰 체감으로.

### 콜백에서 쓰는 변수는 그 콜백보다 먼저 선언해야 한다 (TDZ ReferenceError 로 부팅 전체가 블랙아웃)
- 증상: 카메라 팬/줌을 추가해 배포하니 게임이 통째로 안 뜸 — 생물·버튼·카드·로비까지 전부 안 보임(블랙아웃).
- 원인: `game.onWorldChanged` 콜백 안에 `camX = c0.x` 를 넣었는데, 이 콜백은 `game.start()`에서 곧장 호출된다.
  그런데 `let camX` 선언이 그 아래에 있어 **선언 전 접근 = Temporal Dead Zone ReferenceError**. `boot()`이
  `game.start()`에서 통째로 throw → 이후 `lobby.show()`·`app.ticker.add`(렌더 루프)까지 전부 실행 안 됨 → 완전 블랙.
- 재발 방지책: ① setup 중 즉시 호출되는 콜백(onWorldChanged 등)이 참조하는 `let/const` 는 **그 콜백보다 위에**
  선언한다. ② 타입체크·유닛테스트가 못 잡는 **런타임 부팅 오류는 `npm run smoke`**(헤드리스 chromium 으로 실제
  부팅·관전·카메라 입력을 구동해 pageerror·canvas 유무 확인)로 잡는다. **main/부팅/렌더를 크게 바꾸면 smoke 를
  돌리고 배포**한다. (이 사고는 smoke 로 즉시 잡혔을 것 — 그래서 scripts/smoke.mjs 를 추가했다.)

- 원인: 카드가 `max-width:min(94vw,300px)`로 폭 300까지 늘고, `.hud-row1`이 `space-between`이라 낮밤을 카드
  오른쪽 끝으로 밀었다. 카드 오른쪽 끝(~300px)이 우상단 컨트롤(right:12, 폭 ~101 → 왼쪽 끝 ~277px)과 겹치는데
  컨트롤 z-index(12) > 카드(8)라 컨트롤이 위를 덮는다. 넓은 폰에선 안 겹쳐 재현이 들쭉날쭉.
- 해결(hudPanel.ts): ① 낮밤을 `space-between` 오른쪽 끝 → `flex-start`로 개체 수 바로 오른쪽에 붙인다(컨트롤과
  절대 안 겹침). ② 카드 폭을 `max-width:min(300px, calc(100vw - 128px))`로 컨트롤 앞에서 끊는다.
- 재발 방지책: 좌상단 고정 패널의 **오른쪽 끝**에 정보를 두지 말 것 — 우상단 고정 컨트롤(더 높은 z-index)에 깔린다.
  space-between으로 요소를 패널 끝으로 미는 패턴은 반대편 모서리 위젯과의 충돌을 부른다. 실측(playwright
  boundingBox)으로 좌표 겹침을 확인하면 폰별 들쭉날쭉을 결정적으로 잡는다.

### 접이식 패널이 flex 컬럼(align-items:flex-start)에서도 전체 폭으로 늘어난다
- 증상: 접힌 "종 안내" 범례가 제목 한 줄뿐인데도 화면 전체 폭 바(374px)로 깔려 상단이 꽉 막혀 보인다.
- 원인: `.hud-root`가 `align-items:flex-start`인데도 범례가 콘텐츠 크기로 안 줄고 컨테이너 폭 전체를 차지했다
  (형제 `.hud-timeline-wrap`은 `align-self:stretch`라 전폭이 맞지만, 범례는 그게 없는데도 전폭). align-items만으로
  자식이 shrink-to-fit 된다고 믿으면 안 된다.
- 해결(hudPanel.ts): `.hud-legend`에 `width:fit-content`(+`max-width`)를 명시 → 접힘 84px 칩, 펼침은 종 목록에 맞춰 확장.
- 재발 방지책: 콘텐츠 크기로 줄이고 싶은 오버레이 위젯은 `width:fit-content`를 **명시**한다. align-items:flex-start만
  믿지 말 것. 실제 폭은 playwright boundingBox로 확인.

### 인라인 `style.display` 를 쓰는 패널은 CSS 클래스 규칙으로 못 숨긴다
- 증상: 드래프트 전체 화면이 뜬 동안 HUD(`.hud-root`)와 컨트롤바(`.controls-bar`)가 뿌연 유리 아래 그대로
  남아 비쳐 보였다. 그 위를 덮은 오버레이 때문에 클릭도 먹통(playwright: "draft-root subtree intercepts
  pointer events")이라 자동 검증이 먼저 걸려 넘어졌다.
- 원인: `hudPanel`·`controls` 가 가시성을 `root.style.display = ...` **인라인**으로 관리한다. 새로 추가한
  `body.draft-open .hud-root { display:none }` 는 인라인 스타일보다 우선순위가 낮아 진다.
- 해결(panelStyles.ts): 해당 규칙에 `!important` 를 붙였다.
- 재발 방지책: 전체 화면 오버레이를 새로 띄울 땐 **그 아래 깔린 위젯이 인라인 display 를 쓰는지** 먼저 확인한다.
  쓴다면 CSS 로 숨길 때 `!important` 가 필요하고, 아니면 그 위젯의 `setVisible` 을 phase 로 직접 제어한다.
  반투명 오버레이는 아래 위젯을 "안 보이게" 만들지 못한다 — 비쳐 보인다.

### 고정 크기 히어로 + `grid 1fr` + `min-height:0` → 낮은 창에서 헤더·카드를 덮는다
- 증상: 360×640 같은 짧은 폰에서 드래프트 히어로(메달리온 204×164 + 배지 + 점)가 헤더 제목 위로 올라타고
  아래로는 첫 카드를 덮었다. CTA 는 멀쩡히 보여서 "CTA 가 화면 밖으로 밀리는가"만 보는 검사로는 안 잡힌다.
- 원인: `min-height:0` 인 `1fr` 행은 콘텐츠보다 작아질 수 있고, 그 안의 고정 크기 콘텐츠는 레이아웃을 밀지
  않고 **위아래로 넘쳐흐른다**(flex 가운데 정렬이라 양쪽으로 똑같이).
- 해결(draftPanel.ts `fitHero`): 히어로를 `transform: scale()` 로 남는 높이에 맞춰 줄인다(위아래 14px 여백,
  0.4~1.4 범위). 배율은 바깥 래퍼(`.draft-hero-scale`), 등장 애니메이션(pop-soft, transform 키프레임)은
  안쪽(`.draft-hero-group`) — 한 엘리먼트에 두면 키프레임이 배율을 덮어쓴다.
- 재발 방지책: 겹침 검사는 **콘텐츠 그룹 전체**(배지·점 포함)의 boundingBox 를 헤더 아래끝·카드 위끝과
  비교한다. 대표 자식(메달리온) 하나만 보면 배지가 카드를 덮는 걸 놓친다. 낮은 창(≤640) 을 반드시 넣는다.

### 희귀도 배지는 뽑기 확률과 반드시 묶어야 한다
- 증상(예방): 핸드오프 UI 스펙이 "희귀도 5단계(흔함~전설)" 배지·콘페티를 요구했으나 코드엔 희귀도 개념이

- 재발 방지책: UI 스펙이 새 분류(희귀도·티어·등급)를 요구하면, **그 분류가 게임 규칙에서 실제로 무엇을
  바꾸는지** 먼저 정한다. 순전히 장식이면 그렇게 이름 붙이고, 아니면 규칙에 연결한다. `cards.test.ts` 가

### localStorage 만 진실로 삼으면 저장이 막힌 환경에서 상태가 갈라진다
- 증상: 도전 과제 테스트 4건이 "달성했는데 안 열렸다"로 실패. 원인을 보니 vitest(node)에는 `localStorage` 가
  없어 읽기·쓰기가 통째로 no-op 이었다. 브라우저 사생활 모드에서도 똑같이 터진다 — 종료 화면엔 "달성!"이 뜨는데
  대백과·로비엔 안 뜨는, 화면끼리 어긋난 상태가 된다.
- 원인: `readState()/writeState()` 가 매번 localStorage 를 직접 읽고 쓰는 구조. 저장이 막히면 방금 쓴 값도 못 읽는다.
- 해결(`game/achievements.ts`): **메모리 캐시를 진실로, localStorage 를 그 사본으로.** 첫 읽기에서 하이드레이트하고
  쓰기는 캐시 먼저 갱신한 뒤 저장을 시도한다. 저장이 실패해도 이번 세션 안에서는 일관되다(다음 실행에만 잊는다).
- 재발 방지책: 영속 상태를 새로 만들 땐 저장소를 캐시의 사본으로 다뤄라. `game/meta.ts` 도 같은 구조라 같은 결함이
  남아 있다(메타 경험치가 사생활 모드에서 세션 중에도 안 쌓인다) — 고칠 때 참고.

### 스프라이트 아래 레이어(playerG)에 그리는 표식은 몸 안쪽이면 통째로 가려진다
- 증상: 「별가루」 꾸밈이 화면에서 거의 안 보였다. 코드는 정상이고 알파도 0.95 였다.

### 드래프트 스크린샷은 오버레이만 걷어내면 된다(월드가 이미 멈춰 있다)
- 상황: 꾸밈을 촬영하려는데 레벨업 드래프트가 계속 끼어들어 월드를 가렸다. 일시정지 버튼은 메뉴 오버레이를 띄워
  화면을 덮고, 카드를 고르면 곧 다음 드래프트가 떴다.
- 요령: 드래프트 중에는 `world.step()` 이 멈추고 캔버스는 계속 그려진다. 그래서 `.draft-root { display:none }` 을
  주입하고 캔버스에서 `game-view-frosted` 클래스만 빼면 **정지한 무리 위에서 꾸밈 애니메이션만 도는** 깨끗한
  화면이 된다. 개체가 안 움직여 프레임 타이밍을 맞출 필요도 없다.

### 카드 설명이 sim 과 어긋나 있었다 — 「날개」는 혼자서 날지 못했다
- 증상: 「날개」 카드 설명은 "산과 바다 위를 날아 넘고"인데 실제로는 `wings 0 → 42` 라 비행 문턱(65)을 못 넘어
  **아무 일도 일어나지 않았다**. 게다가 `wings` 는 sim 전체에서 `>= flyThreshold` 문턱 비교에만 쓰여
  수치의 크기가 무의미했고, 그래서 「날개」(+42)와 「튼튼한 날개」(+30)는 사실상 같은 카드였다("날개 포인트").
- 원인: 관문/강화라는 **등급 서사만 있고 sim 근거가 없었다.** 수영·초음파·독·원거리는 모두 수치가 의미를 갖는데
  (문턱 2개, 반경, 지속 피해, 사거리) 날개만 켜짐/꺼짐이었다.
- 해결: ① 「날개」를 `flyThreshold + 3` 으로 올려 한 장으로 실제로 날게 했다. ② `flyDrainMultiplier(wings)` 를 만들어
  날개가 클수록 비행 대사가 줄게 했다(문턱에선 기존 값 그대로 → 기존 밸런스 보존). ③ 「튼튼한 날개」에
  `requiresTrait` 를 붙여 **이미 나는 종에게만** 나오게 했다. 안 그러면 못 나는 종이 골라 아무 일도 안 일어난다.
- 재발 방지책: 카드 설명에 "무엇이 된다"고 쓸 땐 **그 카드 한 장으로 그 일이 실제로 일어나는지** 수치로 확인한다.
  능력형 카드를 관문/강화로 나눌 땐 sim 이 그 수치의 크기를 실제로 읽는지 먼저 본다. `cards.test.ts` 가
  "관문 한 장으로 문턱을 넘는다"를 강제한다.

### 설명 길이에 따라 카드 레이아웃이 카드마다 달라졌다
- 증상: 드래프트 카드 중 「다산」처럼 설명이 짧은 카드만 스탯 칩이 설명과 **같은 줄 오른쪽**에 붙어, 카드마다
  레이아웃이 제각각으로 보였다.
- 원인: `.draft-card-body { flex-wrap: wrap; justify-content: space-between }`. 설명 + 칩이 한 줄에 들어가면
  나란히 놓이고, 안 들어가면 칩이 다음 줄로 넘어간다. 스펙 목업은 설명이 짧아 나란한 모습만 보여줬다.
- 해결(panelStyles.ts): `.draft-card-desc { flex: 1 1 100% }` — 설명이 항상 제 줄을 통째로 쓴다. 데스크톱은 세로
  배치라 `flex-basis` 가 높이가 되므로 `flex: 1 1 auto` 로 되돌린다.
- 재발 방지책: `flex-wrap` + `space-between` 은 **콘텐츠 길이에 따라 레이아웃이 바뀐다.** 목업의 문구 길이만 보고
  판단하지 말고, 실제 데이터(가장 짧은 것·가장 긴 것)로 확인한다. playwright 로 칩의 top/left 를 재면 결정적으로 잡힌다.

### 전체 화면 오버레이는 ?dev 패널도 덮는다(반대로, dev 패널이 오버레이를 덮는다)
- 증상: `?dev` 로 켠 디버그 패널(z-index 31)이 드래프트 화면(z-index 15) 위에 떠서 첫 카드의 이름을 가렸다.

- 재발 방지책: 전체 화면 오버레이를 만들면 **그보다 z-index 가 높은 고정 위젯이 있는지** 훑는다(hud·controls·dev).

### ▲=이득 / ▼=손해 규칙이 안 맞는 형질이 있다 (대사·식성)
- 증상: 「올빼미 눈」의 `▼ 대사 -8` 이 빨강(손해)으로 떴지만 실제로는 이득이다("기운을 아낀다").
  반대로 「뜨거운 피」의 `▲ 대사 +14` 는 초록인데 더위·가뭄에서는 손해다. 식성도 같다 — 초식/육식 중
  어느 쪽도 더 낫지 않은데 `식성 +22` 가 초록, `-22` 가 빨강으로 떴다.
- 원인: 칩 색을 **부호**로 정했다(`up ? 초록 : 빨강`). 대부분의 형질은 "많을수록 좋다"라 맞지만,
  대사는 추위↔더위 절충이고 식성은 스펙트럼이다. 어느 쪽이 이득인지는 이번 판 환경과 다가오는 대멸종이 정한다.

  스탯 델타 오버레이가 전부 같은 규칙을 쓴다.
- 재발 방지책: 색으로 가치 판단을 표시할 땐 **그 형질에 정말 좋은 방향이 있는지** 먼저 묻는다.
  새 형질을 넣을 때 절충형이면 `NEUTRAL_TRAITS` 에 추가한다(`traitDisplay.test.ts` 가 풀 전체를 훑어 강제).

### 사냥 판정에 쿨다운이 없어 접촉 즉시 즉사였다
- 증상(설계 결함): `stepEntity` 가 사거리에 닿는 **매 틱** 즉사 판정을 굴렸다. 호각(공격력 같음)이면 성공 확률

- 해결(`sim/behavior.ts` · `sim/entity.ts`): `attackCd`(물기 쿨다운) + `biteOutcome(공격력, 먹잇감 공격력)` 순수 함수.
  못 죽인 물기는 기운을 깎고(`bite` 연출), 체급 차가 `biteIgnoreDiff` 넘게 밀리면 이빨이 아예 안 박힌다.
- 재발 방지책: "매 틱 굴리는 확률"은 사실상 즉시 성공이다(1 - (1-p)^n → 빠르게 1). 확률 판정에는 반드시
  쿨다운이나 1회성 게이트를 붙인다. `world.test.ts` 가 `attackCooldownTicks > 1` 과 접촉→사망 시간을 강제한다.

### 대멸종 필터가 포식 압력에 몰래 기대고 있었다
- 증상: 사냥을 약하게 바꾸자 "저대사 종은 한파를 못 넘는다" 테스트가 경계에서 깨졌다(통과기준 3인데 3마리 생존).
  추위가 아니라 **포식자가** 저대사 종을 마저 솎고 있었던 것이다.
- 해결: 파라미터 튜닝의 제약조건을 "필터가 또렷이 갈린다(고대사 통과·저대사 탈락)"로 두고 쓸었다.
  최종값(bias 0.34 · scale 1.5 · 물기 18 · 쿨다운 3)에서 필터는 오히려 더 또렷해졌다(고대사 11 vs 저대사 0).
- 재발 방지책: 포식·대사·환경 중 하나를 만지면 **나머지 둘의 통과기준 테스트를 지표로 함께 잰다.**
  프로브를 임시 vitest 파일로 짜서 `SIM` 을 런타임에 바꿔가며 쓸면 몇 분 만에 격자를 훑을 수 있다.

### 카오스 생태에서 "최종 개체 수"는 노이즈 지배 — 피크·생존시드수로 판단하라
- 증상: "큰 사냥·긴 포만"(carnGorge) 튜닝 프로브에서 같은 파라미터(B=1 R=60)가 4시드(env-1~4) 잡식
  최종 13.5, 8시드(env-1~8) 최종 8.9 로 요동쳤다. 최종값만 보면 "gorge 가 잡식을 5씩 깎는다"로 오판해
  값을 과하게 낮출 뻔했다. 실제론 잡식 최종은 시드마다 0~25 로 흩어지는 카오스 꼬리라, 파라미터 효과보다
  시드 노이즈가 훨씬 크다.
- 원인: 소수 개체 + 붐-버스트 생태는 3000틱 시점의 "최종 개체 수"가 카오스적(초기 미세차가 증폭). 평균을
  내도 시드 수가 적으면 안 수렴한다. 반면 **피크(성장 능력)**·**생존시드수(자생 여부)**는 안정적 지표다.
- 재발 방지책: 밸런스 프로브에서 종의 "건강"을 최종 개체 수 하나로 재지 말 것. ① 조기 붕괴 여부는 **피크**
  (전 구간 24~25 유지면 성장은 멀쩡, 최종 노이즈는 꼬리) ② 자생 여부는 **생존시드 n/N**(0/8→4/8 처럼
  이산적이라 노이즈에 강함) ③ 최종 평균은 방향 참고만. 하드 제약(대멸종 필터)은 어차피 단일 시드 테스트라
  그걸로 확정한다.
  맵 크기(`world.test.ts` 는 540×960, 실제 게임은 2배)를 반드시 맞출 것 — 안 맞추면 기준선도 재현이 안 된다.

### 먹잇감 조준에 "닿을 수 있는가" 검사가 없었다 (물가 머리박기)
- 증상: 균형 잡식 종이 바다 경계에서 물가에 머리를 박고 서성인다. 프로브: env-1 에서 **내 종 개체틱의 31%**가
  물속 먹잇감(대부분 물 전용 물고기)을 조준하는 데 쓰였다. 들어갈 수도 물 수도 없는데.
- 원인: `nearestFood` 는 후보 필터에서 먹이 종류·통행을 걸렀는데, 먹잇감(`chooseGoal` 의 `grid.nearestMatching`)은
  **감지되는가**만 봤다. 지형 통행 가능성을 안 봤다. 게다가 히스테리시스(`targetKeepFactor`)가 그 목표를 붙든다.
- **끼임 감지(`stuckTicks`)로는 안 풀린다.** 주석에 "물가 먹이에 억지로 들이대다 갇히는 것을 푼다"라고 적혀
  있지만, 물가에서 튕기며 진동하면 이동량이 `stuckMinMove`(0.06)를 넘어 "움직였다"로 판정된다.
  프로브로 확인: `stuckLimit` 은 2000틱 × 여러 시드에서 **한 번도 도달하지 않는다**(사실상 죽은 코드).
- 해결(`sim/behavior.ts`): `chooseGoal` 의 먹잇감 후보와 목표 유지 조건에 `terrain.isPassable(...)` 추가.
  같은 부류인 도망 판정(`computeFlee` 의 포식자 후보)에도 같은 가드를 넣었다(현재 0건이지만 육식 수생종이 생기면 터진다).
- 재발 방지책: **형제 코드끼리 필터를 맞춰라.** 먹이 후보와 먹잇감 후보는 같은 제약(감지 + 통행)을 받아야 한다.
  "안전장치가 있으니 괜찮다"고 넘기지 말고, 그 안전장치가 **실제로 발동하는지 프로브로 세라**.
  `world.test.ts` 가 "물속 먹잇감 조준 비율 < 0.5%"를 강제한다.

### 식성(diet)은 능력을 잠글 뿐, 아무 이득도 주지 않는다 (설계 공백)
- 사실: sim 전체에서 `diet` 가 하는 일은 셋뿐이다.
  `canHunt = diet > 35` · `canGraze = diet < 70` · "저 종은 포식자다"(도망 판정, `diet > 35`).
  `foodEnergy`(33)와 `predationEnergy`(36)는 **식성과 무관한 상수**다.
- 결과: 잡식(diet 50)은 사냥과 채집을 **둘 다 100% 효율로** 한다. 특화는 순손해다.
  · 「포식 본능」(식성 +22): 50 → 72 > 70 → **초식 능력 상실**. 얻는 건 공격력 +4.
  · 「초식 본능」(식성 -22): 50 → 28 < 35 → **사냥 능력 상실**. 얻는 건 번식력 +3.
  둘 다 잡식 종에겐 함정 카드다. 사용자가 "공격 +11 대신 이걸 고를 유인이 뭐냐"고 물은 그대로다.
- 프리셋도 마찬가지: 8개 중 **6개가 사실상 잡식**이다(omni 50 · scout 40 · sea 40 · sky 40 · ranged 60 ·
  **hunter 68 < 70 이라 풀도 뜯는다**). 진짜 초식은 herd(16)·venom(26)뿐이고, 진짜 육식은 하나도 없다.
- 고칠 방향(밸런스 결정 필요): 섭취 효율을 식성에 연동한다. 초식일수록 풀에서 얻는 에너지가 크고, 육식일수록
  사냥에서 얻는 에너지가 크며, 잡식(50)은 양쪽 다 중간. "제너럴리스트 페널티"라는 고전적 해법이고,
  이걸 넣어야 식성 카드와 특화 프리셋에 의미가 생긴다. 먹이 경제가 통째로 바뀌므로 대멸종 필터를 제약으로
  두고 프로브로 튜닝할 것.
- **→ 2026-07-11 해결(78598b5):** `grazeEfficiency`/`huntEfficiency` 순수 함수로 연동. 곡선을 특화 끝
  (순수 초식 ≤35 / 순수 육식 ≥70)에서 1.0 으로 평평하게, 잡식 구간(35~70)만 페널티(`dietSpecializationPenalty`
  0.3). 야생 초식·포식 생태 보존(효율 불변) + 대멸종 필터 3종 유지. 「포식/초식 본능」이 사냥/채집 효율 최대
  이득을 갖고, hunter 프리셋(68)은 사냥 98%·채집 72%라 "사냥꾼" 정체성이 효율로 뒷받침된다.

### 순수 육식 자생은 사냥 "수입" 상향으로 안 풀린다 — 병목은 사냥 성공 빈도 + 이주 부재
- 증상: 식성 효율 연동 후 순수 육식(diet 85, 채집 완전 차단) 내 종이 단독 멸종(프로브 pop 0, peak≈시작 18에서
  안 늚). 사냥 수입(huntEfficiency 보너스)을 2.3배까지 올려도, 보조 형질(speed·attack·vision↑)을 줘도 pop 0.
- 원인: 병목은 사냥 "수입"이 아니라 "성공 빈도"다. ① 야생 초식이 내 종(순수 육식)을 포식자로 보고 도망치는데
  내 종 speed 50 으론 못 따라잡는다. ② 채집 fallback 이 없어 첫 사냥 전에 굶어 죽는다(사망 원인 굶주림 16.8 vs
  포식 0.3). ③ 야생 포식자(같은 diet 85)조차 자생이 아니라 이주(immigrationFloor 4)로 연명한다 — 내 종은
  플레이어라 이주가 없다.
- 결론: 이 게임 구조(소수 개체·채집 풍부·먹잇감 도망·플레이어 이주 없음)에서 순수 육식 자생은 근본적으로
  어렵다. hunter 프리셋(diet 68, 채집 병행)이 pop 37 로 번성하는 게 정답 — "육식 빌드"의 현실적 형태는 채집을
  조금 남긴 diet 68~69 다. 순수 초식은 반대로 grazeEfficiency 1.0 + 다산·무리(herd 프리셋)로 이미 자생한다
  (병목이 포식이라 채집 효율이 아니라 개체수/속도로 푸는 것).
- 재발 방지책: 순수 육식 자생을 만들려면 사냥 수입 상수(`predationEnergy`·huntEfficiency)가 아니라 사냥 성공
  생태(먹잇감 도망 완화 / 먹잇감 밀도↑ / 플레이어 이주)를 손봐야 한다 — 야생 밸런스 대공사라 리스크 크다.
  수입 상향으로 순수 육식을 살리려는 시도는 **효과 없음이 프로브로 확인됐으니 반복하지 말 것**.

### smoke 스크립트가 Windows 에서 vite preview 서버를 orphan 으로 남긴다 (프로세스 실수)
- 증상: `node scripts/smoke.mjs` 가 exit 0 으로 끝났는데 포트 4199 preview 서버(node 2개: npx-cli + vite.js)가
  계속 돈다. 사용자 화면에 "백그라운드 작업이 90분 넘게 돌고 있다"로 보여 불안을 줬다.
- 원인: smoke.mjs 가 `spawn("npx", ["vite","preview",...])` 로 띄우고 끝에 `preview.kill()` 하는데, Windows
  에선 npx(부모)만 죽고 실제 vite.js(자식)가 detached orphan 으로 남는다(프로세스 트리째 안 죽는다).
- 재발 방지책: smoke 를 돌린 뒤 포트 4199 를 물고 있는 node 가 남았는지 확인하고 정리한다
  (`Get-CimInstance Win32_Process -Filter "name='node.exe'" | ? CommandLine -like '*4199*'` → 그 PID 만 Stop-Process).
  **blanket kill(포트 무관 node 전멸) 금지** — 다른 세션 dev 서버까지 죽인다. 근본 고치려면 smoke.mjs 의 spawn 을
  프로세스 그룹으로 띄워(`detached:true`) `process.kill(-pid)` 하거나 tree-kill 로 자식까지 정리한다.
  (Windows: `Stop-Process -Id` 는 부모만 죽이고 detach 된 자식 vite 가 남는다 → `taskkill /PID <부모> /T /F` 로 트리째.)

### 수영 카드로 물 전용(90+)이 되면 육지 종이 땅에 갇혀 죽는다 (전환 시 재배치 없음)
- 증상: 육지에서 살던 내 종이 「지느러미」를 얻으면 뭍에서 냅다 굶어 죽는다(사용자 발견, 2026-07-11).
- 원인: swimming ≥ aquaticOnlyThreshold(90)면 물 전용(canLand=false)이 돼 육지 타일이 통행 불가가 된다.
  「지느러미」(+22)가 바다 프리셋(88)이나 「물갈퀴」(+16) 누적에 더해져 90 을 넘기면, 육지에 있던 무리가
  갑자기 물 전용이 돼 땅에 갇힌다 — 바다로도 못 가고 육지 먹이도 못 먹어 아사. 물 전용 전환 자체는 "바다
  개척자" 빌드로 의도됐으나, 런 중 카드 전환 시 개체를 바다로 옮기는 처리가 빠져 함정이 됐다.
- 해결(applyCard): 내 종 swimming 을 aquaticOnlyThreshold-1(수륙양용 상한)로 막는다(사용자 방향: "수륙양용이되
  바다까지 들어가게만"). 카드로는 물 전용이 안 되고 수륙양용(바다+육지)까지만. 진짜 물 전용은 야생 물고기
  떼만(카드 없어 상한 안 거침). **TRAIT_CEILING[swimming] 을 낮추는 방법은 안 된다** — clampGenome 을 통과하는
  야생 물고기(95)까지 잘라 물 전용을 없앤다. 카드 경로(applyCard)에서만 막아야 한다.
- 재발 방지책: 형질이 "지형 통행 자격"을 바꾸는 문턱(swimming·wings)을 카드로 넘길 때, 그 전환이 개체를 못
  가는 지형에 가두는지 본다. 통행 자격을 잃게 하는 방향(육지→물전용)은 재배치나 상한이 필요하다.

### `world.population` 은 야생 포함 **전체** 개체 수다 — 내 종은 `playerPopulation`
- 증상: 무리 방어 프로브에서 "pop 80"을 내 종 개체 수로 읽고 "다산 초식은 평상시엔 잘 산다"고 오진했다.
  실제로는 내 종이 2~5마리(8시드 중 3~6이 멸종)였고, 80은 야생 98마리를 포함한 값이었다. 그 위에서
  "이웃이 0.5명뿐"이라는 측정이 나와 코드 버그를 의심하며 한참 헤맸다 — 이웃이 없던 게 아니라
  **개체가 없었다**.
- 원인: `get population()` = `entities.length`(전 종). 승패 판정에 쓰는 건 `playerPopulation`(내 종만).
  이름이 짧고 자연스러워 프로브에서 무심코 집는다.
- 재발 방지책: **프로브에서 내 종을 볼 땐 반드시 `playerPopulation`**. "개체 수"를 찍을 때 그게 누구
  개체 수인지 한 번 더 본다. 2026-07-13 세션의 "시야 10 은 보스가 없어도 비생존 빌드" 함정과 같은 계열이다
  — 기준선·대상 없이 절대 숫자만 보면 오독한다.

### 무리 방어를 "물기 확률을 깎는" 방식으로 만들면 아무 일도 안 일어난다 (잡히는 개체는 이미 낙오자)
- 증상: "같은 종 이웃이 많을수록 사냥당할 확률이 떨어진다"를 `biteOutcome` 의 즉사 확률·피해에 저항을
  곱하는 방식으로 구현했더니, 저항이 50% 걸리는데도 잡아먹힘이 29→22 에 그치고 도달 단계·승률이 **전혀**
  안 변했다(승리 0/8 불변).
- 원인: **잡히는 개체는 이미 무리에서 떨어져 나온 낙오자다.** 무리 한가운데 개체는 애초에 잘 안 잡히고,
  잡히는 건 먹이를 찾아 홀로 나선 개체 — 그 개체는 이웃이 0~1 이라 "이웃 수" 보정이 걸리지 않는다.
  전체 개체 평균 저항(51%)만 재고 "방어가 잘 걸린다"고 오판했다. **물린 뒤가 아니라 물리기 전에** 막아야 했다.
- 해결: 표적 선택(`chooseGoal`)에서 뭉친 무리 개체를 **후보에서 통째로 제외**(이진 판정 `herdShielded`).
  사자가 물소 떼를 안 덮치는 것과 같다. 도달 2.0 → 4.0, 잡아먹힘 24 → 13.
- 재발 방지책: 확률 보정형 방어를 설계할 때 **"그 보정이 실제로 죽는 개체에게 걸리는지"** 를 먼저 본다.
  평균이 아니라 **사망 사건 시점의 값**을 재야 한다. 무리·군집처럼 "안전한 개체와 위험한 개체가 공간적으로
  갈리는" 메커니즘은 특히 평균이 거짓말을 한다.

### 초식 프리셋의 병목을 "먹이"로 지레짐작하면 안 된다 — 사인(死因)을 먼저 본다
- 증상: 다산 초식이 번식을 못 하는 걸 보고 "순수 초식이라 유한한 먹이를 야생 초식 98마리와 나눠 먹어
  에너지가 번식 문턱(78)에 못 닿는다"고 진단, **무리 채집**(뭉치면 채집 수입 +60~120%)을 만들었다.
  효과 0(도달 3.4 vs 3.6, 승리 0/8).
- 원인: 사인 집계를 보면 **굶주림 사망이 4~7 뿐**이고 잡아먹힘이 24~34 였다. 먹이는 병목이 아니었다.
  번식이 적었던 건 에너지가 모자라서가 아니라 **개체가 번식 전에 잡아먹혀서**였다. 인과를 거꾸로 읽었다.
- 재발 방지책: 프리셋·빌드가 약하면 **먼저 `world.deaths` 사인 집계를 찍는다**(단계별 개체 수 추적도 함께).
  "왜 약한가"를 추측으로 정하고 메커니즘을 만들면 멀쩡한 코드를 짜고도 아무 일도 안 일어난다.

### 새 형질을 추가할 땐 `TRAIT_KEYS` **맨 끝**에 + 종 생성에서 **rng 없이** 설정한다 (게놈 v7 에서 재확인)
- 증상(예방됨): 형질을 추가하면 `TRAIT_KEYS` 를 순회하며 rng 를 뽑는 곳(`makeKinSpecies`·`generateWildSpecies`·
  `makeMapSpecies`·`makeBiomeSpecies`·야생 진화 드리프트)이 **rng 를 더 소비**해 스트림이 밀린다 → 야생 형질이
  통째로 달라지고 대멸종 필터·보스 통과기준이 무너진다.
- 재발 방지책: ① 새 키는 **맨 끝**에 붙인다 ② 위 다섯 곳의 "rng 없이 설정" 분기에 새 키를 **반드시 추가**한다
  (`if (key === "size" || key === "camouflage") { ... continue; }`) ③ 변이 목록(`MUTABLE_TRAITS`)의 **개수를
  유지**한다 — 독립 스트림(mutRng)이라도 소비 **횟수**가 바뀌면 개체 변이 결과가 통째로 이동한다.
  v7 은 herding 을 빼고 size 를 넣어 6개를 유지했다.
- 그리고 **새 형질의 기본값이 "중립"이 되게 설계한다**: 몸집은 50 에서 모든 보정이 정확히 0 이고(±(size-50)/50
  에 곱함) 은신은 0 이면 영향이 없다. 그래서 v7 을 통째로 얹고도 305 테스트가 그대로 통과했다. 기본값이
  중립이 아니면 새 축을 넣는 순간 기존 밸런스가 전부 이동한다.

### 새 형질의 "대가"를 여러 개 겹치면 함정 카드가 된다 (몸집이 처음에 그랬다)
- 증상: 몸집(size)에 대가를 셋(느림 0.25 · 대식 0.4 · 저번식 0.4) 걸었더니 **큰 몸이 순손해**였다 —
  몸집 85 초식이 8시드 중 7 멸종(내 종 0.6마리 vs 무방비 5.5). 잡아먹힘은 27→15 로 줄어 방어는 분명히
  작동했는데, 느려서 먹이를 못 찾고 · 많이 먹어 굶고 · 새끼로 메우지도 못하는 **삼중고**가 이득을 삼켰다.
- 원인: 대가 셋이 **곱해져서** 걸린다는 걸 간과했다. 하나하나는 온건해 보여도 합치면 종이 못 산다.
  특히 초식은 "번식으로 사는" 종이라 번식 페널티가 치명적이다.
- 해결: 대가를 절반 가까이 낮추고(0.08 / 0.12 / 0.18) 방어 이득(sizeBiteWeight)을 0.8 → 1.4 로 키웠다.
  무방비 6.6 → 몸집 85 는 9.0 · 몸집 100 은 22.6(잡아먹힘 24→5).
- 재발 방지책: 형질 하나에 대가를 여러 개 걸 땐 **각각을 온건하게 잡고 프로브로 합산 효과를 먼저 잰다.**
  "이득 하나 vs 대가 셋"은 거의 항상 대가 쪽이 이긴다.

### 순수 육식은 "채집 절벽"에서 죽는다 — 식성 70 을 넘는 순간 종이 무너진다 (구조적 결함)
- 증상(사용자 지적, 2026-07-14): *"육식이 확실히 초식보다 훨씬 유리한 것 같아. 애초에 시작이 완전
  육식이 아니라 잡식으로 돼있어서 그런가?"* — 정확했고, 실상은 더 나쁘다. 프로브(8시드):
  | 식성 | 사냥/채집 효율 | 도달 | 승리 |
  |---|---|---|---|
  | **68 (잡식 상단 · 현재 프리셋)** | 98% / 72% | **6.9** | **7/8** |
  | 74 (순수 육식) | 100% / 0% | 2.6 | 0/8 |
  | 85 | 100% / 0% | 2.1 | 0/8 |
- 원인: `canGraze = diet < dietGrazeMax(70)` 가 **이진 절벽**이다. 식성 69 는 채집 효율 72% 인데
  70 이 되는 순간 **0%** 가 된다 — 1 포인트 차이로 먹이의 절반이 사라진다. `grazeEfficiency` 곡선
  자체는 연속인데 통행 게이트가 절벽을 만든다.
- 결과 ① 「날쌘 육식 사냥꾼」은 이름과 달리 **육식이 아니라 잡식 상단**이다(식성 68). 사냥 98% + 채집
  72% 로 **양쪽을 다 먹는 게 최적해**라, "육식 특화"는 순손해다.
  결과 ② 카드로 식성을 올리면(「포식 본능」류) 70 을 넘는 순간 종이 죽는다 — **낚시 카드**다.
- **→ 2026-07-15 해결(후보 ① 채집 연속화).** `canGraze` 이진 게이트(`diet < 70`)를 없애고 효율 기반으로
  바꿨다(`grazeEfficiency(diet) > grazeMinEff`). `grazeEfficiency` 에 diet 70 위 tail 을 넣어 채집 효율이
  뚝 끊기지 않고 완만히 0 으로 준다(`carnGrazeFalloff` 3: diet 74=46% · 85=9% · 90=3% · 100=0%). 순수 육식이
  사냥 사이에 풀도 뜯어 연명한다 — known_issues "채집 fallback 부재" 병목을 직접 푼 것.
  · **효과(프로브 6시드·3000틱):** diet 74 최종 0(멸종) → **67(자생)** · diet 85 최종 0 → 7(연명).
  · **밸런스 완전 보존:** diet 70 아래(모든 프리셋·야생 초식)는 tail 이 없어 불변 — 프리셋 도달이 변경
    전과 **소수점까지 동일**(6.4/5.8/6.0/6.7). 야생 포식자(diet 85)는 채집 9% 만 얻어 개체수 불변~감소
    (55→53). 대멸종 필터·보스 통과기준 116 테스트 통과.
  · **왜 falloff 를 급하게(3) 잡았나:** 완만하면(falloff 2, diet 85=17%) 야생 포식자가 채집으로 살찌워져
    생태가 통째로 바뀐다. 급한 tail 이 "순수 육식 fallback 은 주되 야생 포식자엔 안 가게"의 균형점.
  · diet 85 가 여전히 약한 건(최종 7) 의도적이다 — known_issues "깊은 순수 육식 자생은 근본적으로 어렵다"
    (먹잇감 도망·플레이어 이주 없음)와 일치. **절벽(즉사)만 없애면 충분**이고, 억지로 강화하면 야생 밸런스가
    흔들린다. 후보 ②(사냥 수입 상향)는 이미 실패했고, ③(잡식 이점 깎기)은 대멸종 필터를 깬다.

### 새끼를 한 마리 더 낳는 식의 "정점 보상"은 rng 스트림을 민다 (쌍둥이 실패)
- 증상: 정점 번식력(100) 보상을 **쌍둥이**(한 배에 둘)로 만들었더니, 쌍둥이 종의 개체 수가 오히려
  **적게** 나왔다(45 vs 99 짜리 65). "쌍둥이가 손해"처럼 보였지만 그게 아니었다.
- 원인: 새끼를 하나 더 낳느라 `world.rng.range` 를 **두 번 더 소비**해 스트림이 밀렸다. 그 뒤 모든
  난수(배회·번식·사냥 판정)가 어긋나 **시뮬이 통째로 다른 세계**가 됐다. 45 와 65 는 좋고 나쁨의
  비교가 아니라 그냥 다른 전개였다.
- 해결: 문턱을 낮추는 방식으로 바꿨다(`apexBreedRelief` — 번식에 필요한 기운 ×0.7). rng 소비가
  그대로라 안전하고, 효과는 오히려 더 확실하다(번식 빈도 자체가 오른다).
- 재발 방지책: **개체를 생성/삭제하거나 난수를 더 뽑는 보상은 rng 스트림을 민다.** 같은 효과를
  "기존 판정의 계수/문턱을 바꾸는" 방식으로 표현할 수 있는지 먼저 본다. 꼭 필요하면 독립 rng 로.

### 야생 포식자의 몸집은 밸런스의 기준점이다 — 여기만은 건드리지 말 것
- 증상: 야생종에 몸집 다양성을 주면서 포식자를 64(맹수답게 크게)로 올렸더니, 대멸종 필터 테스트와
  개체 진화 테스트가 깨졌다(내 종 몰살).
- 원인: `sizeBiteWeight`(1.4)가 몸집 차를 공격력 차보다 크게 싣는다. 포식자 몸집 50 → 64 면 내 종
  (50)을 무는 즉사 확률이 **0.64 → 0.93** 으로 뛴다. 14 포인트가 공격력 20 포인트만큼 실린 셈.
- 재발 방지책: 야생 포식자의 `size` 는 **기준선 50 유지**. 다른 야생종(작은 풀벌레 30·느린 거북 68)은
  자유롭게 줘도 된다 — 포식 판정의 한쪽 항이 아니기 때문이다. "큰 맹수"가 그럴듯해도 이 항은 건드리면
  전 밸런스가 이동한다.

### 번식 문턱을 낮추는 "보상"은 자해다 — 먹이가 유한한 세계에서 "더 자주 낳기"는 보상이 못 된다
- 증상: 정점 번식력(100) 보상을 `apexBreedRelief`(번식 문턱 78 → 54.6)로 만들었는데, 정점 종이
  **99 짜리보다 약했다**(6시드·1500틱: 평균 개체 수 121 vs 127 · 최종 93 vs 138). 7장을 써서 100 을
  찍은 보상이 개체 수를 **깎는** 함정 카드였다.
- 원인: 새끼는 어미 기운의 절반을 떼어 간다(`childEnergy = e.energy * 0.5`). 문턱을 낮추면 **기운이
  모자란 채로 낳아 어미와 새끼가 둘 다 반쯤 굶은 상태로 갈라진다.** 굶주림 사망 125 → **176**.
  피크만 오르고(192 → 198) 평균은 떨어지는 전형적인 붐-버스트 — 먹이가 유한하니 **상한은 먹이가
  정한다.** 더 낳아 봐야 굶어 죽는 회전율만 오른다.
- 해결: 문턱(78)은 그대로 두고 **어미가 치르는 대가만** 깎았다(`apexBreedCost` 0.6 — 기운의 50% 대신
  30% 만 잃는다). 기운이 넉넉할 때만 낳는 규칙이 그대로라 굶는 새끼가 안 늘고, 어미가 살아남아 다음
  번식에 더 빨리 닿는다. 피크·평균·최종이 **전부** 99 보다 높아졌다(210/137/136 vs 180/116/107).
- 재발 방지책: **번식 관련 보상은 "더 낳게" 하지 말고 "낳고도 살아남게" 하라.** 그리고 이 종류의
  보상은 **최종 개체 수 하나로 재면 안 된다** — 붐-버스트는 마지막 틱이 골짜기에 걸리면 더 강한 종이
  더 약해 보인다. **피크·평균·사인 집계를 함께** 찍는다.

### 정점 고정 + 개체 변이 = 래칫 (고정만 넣으면 형질이 슬금슬금 100 으로 샌다)
- 증상: "정점(100)은 안 내려간다"만 넣었더니, 기준선이 **99 인 종의 살아있는 개체 평균 번식력이
  99.20** 까지 올라갔다. 화면(설계도·드래프트)엔 "99"라 써 있는데 실제 무리는 정점을 누리고 있었다.
- 원인: 변이(±1.5)가 99 짜리 새끼의 **1/3 을 반올림으로 100 에 얹는데**, 고정이 그걸 영영 붙잡는다.
  세대가 지날수록 100 짜리 개체만 쌓인다(한 방향 래칫).
- 해결: 변이가 정점을 **갉지도, 만들지도** 않게 했다(`genome.mutateGenome`: 부모가 100 이면 새끼도
  100 / 부모가 99 이하면 새끼는 최대 99). 정점의 유일한 입구는 **카드**다. 대신 카드로 기준선이 100 에
  닿는 순간 `game.pickCard` 가 **살아있는 무리 전체를 100 으로 스냅**한다 — 개체는 자기 값 기준으로
  감쇠를 받아(변이로 낮은 개체는 같은 카드로 덜 오른다) 안 그러면 기준선만 100 이고 무리는 95~99 에
  흩어진 채 남는다("정점!"이라 외치는데 정작 무리는 효과를 못 누린다).
- 재발 방지책: **"안 내려간다"는 규칙을 넣을 땐 "그럼 뭐가 올려 주는가"를 반드시 함께 막아라.**
  한 방향으로만 열린 문은 시간이 지나면 전부 통과시킨다. rng 는 **정점이라 안 쓸 때도 반드시 뽑는다**
  (소비 횟수 고정 — 건너뛰면 mutRng 스트림이 밀린다).

### 화면 문구는 sim 규칙과 한 쌍이다 — 규칙만 바꾸고 문구를 두면 화면이 거짓말한다
- 증상: 정점 번식 보상을 "문턱 완화" → "어미 대가 완화"로 바꾸면서 `sim/params`·`sim/behavior`·
  대백과는 고쳤는데 **`ui/traitDisplay.APEX_BOON` 을 빼먹었다.** 드래프트 "내 종" 패널이 계속
  **"적은 기운으로도 새끼를 쳐요"**(폐기된 규칙)라 말하고 있었다.
- 원인: 타입도 테스트도 이 어긋남을 못 잡는다(문자열은 컴파일러에게 그냥 문자열이다).
  **실제 앱을 띄워 보고서야** 잡혔다.
- 재발 방지책: sim 규칙을 바꾸면 그 규칙을 **말하는 곳**을 전부 grep 한다(`APEX_BOON`·`glossary`·

### git worktree 에 node_modules 를 junction 으로 걸고 `worktree remove --force` 하면 원본이 지워진다
- 증상: A/B 밸런스 비교를 하려고 임시 worktree 를 만들고 `mklink /J` 로 원본 `node_modules` 를 걸었다.

  (`tsc` 를 못 찾음). `npm install` 로 복구.
- 원인: 재귀 삭제가 junction 을 **따라 들어가** 링크 대상(원본)을 지웠다. Windows junction 은 심볼릭
  링크와 달리 많은 도구가 "진짜 디렉터리"로 취급한다.
- 재발 방지책: worktree 를 지우기 **전에 junction 부터 끊는다**(`rmdir <worktree>\node_modules` — 링크만
  지운다). 또는 아예 링크하지 말고 worktree 안에서 `npm ci` 를 따로 돌린다.
  ⚠ 관련: 공유 워킹 트리에서 `git stash push -- src/` 도 금지다 — 다른 세션의 진행 중 변경까지 휩쓴다
  (CLAUDE.md 동시 세션 루틴). A/B 비교는 **worktree** 로 하되 위 함정을 피할 것.

### 정점 희생 관문(sacrifice)의 안전한 짝은 echo/vision 뿐 — 억지로 만들면 함정 카드다
- 맥락: `sacrifice` 틀(형질을 0 으로 버리고 정점도 뚫는다)이 생긴 뒤, "무엇을 버리고 무엇을 얻는" 관문을
  더 만들려 했으나(backlog ③) 자연스러운 짝이 없어 보류했다.
- 왜 echo/vision 만 안전한가: 초음파는 시야를 **대체**한다(senseRange = max(vision, echoRange)). 그래서
  눈을 버려도 사방을 "듣는다" — 종이 안 죽는다. 다른 형질은 0 으로 만들면 대체 수단이 없어 붕괴한다:
  · **속도 0** → sizeSpeedFactor 까지 겹쳐 사실상 못 움직임 → 먹이 못 찾아 굶어 죽음
  · **번식력 0** → 새끼를 아예 못 침 → 세대교체 실패로 멸종
  · **시야 0**(echo 없이) → 먹이 감지 반경 0 → 굶음
  · **공격력 0** → 육식 전환 불가 + 포식자에게 반격·위협 못 함
  · **무리 0** → 기본이 이미 0 이라 대부분 종엔 무의미(관문급 임팩트 없음)
- 재발 방지책: **sacrifice 관문은 "버린 형질을 대체하는 메커니즘"이 sim 에 있을 때만 만든다.** 그게
  없으면 형질 0 = 종 붕괴라, 카드 설명은 근사한데 뽑으면 지는 함정이 된다. 새 sacrifice 짝을 넣으려면
  먼저 그 대체 메커니즘(초음파가 시야를 대신하듯)부터 sim 에 있는지 확인할 것. backlog 의 "물 → 뭍 전환"
  예도 부적합하다 — swimming 을 0 으로 버리는 게 아니라 **올려야** 하는 방향이고, 카드 상한(89)에 막혀
  물 전용 문턱에 못 닿는다.

## 모드 분기는 "기능이 켜졌나"가 아니라 "사람이 실제로 개입했나"에 걸어야 한다 (2026-08-01)

## em dash 검사를 bash `$'\u2014'` 로 하면 거짓 음성이 난다 (2026-08-03, 프로세스)
- 증상: 전역 규칙(em dash 금지, 커밋 메시지 포함)을 어긴 채 문서와 커밋 메시지를 쓰고,
  `grep -c $'\u2014'` 로 자체 검사해 **"저장소 전체 0건"** 을 받고 통과로 착각했다. 실제로는 그 자리에서
  방금 쓴 글에 12곳이 있었다.
- 원인: Git Bash 환경에서 `$'\uXXXX'` 이스케이프가 의도한 UTF-8 바이트로 안 풀려(로케일 추정) 패턴이
  아무것도 안 맞았다. 검사가 아니라 **검사기가 고장 나 있었다.**
- 재발 방지책: 대시 검사는 **python 으로 코드포인트를 직접 센다.**
  `python -c "import io;print(io.open(P,encoding='utf-8').read().count(chr(0x2014)))"`
  또는 Grep 툴(ripgrep)에 문자를 그대로 넣는다. **문서와 커밋 메시지를 쓴 직후, 커밋 전에 센다.**
  더 일반화하면: **검사가 0을 돌려주면 먼저 검사기를 의심하라.** 아는 양성 사례 하나로 검사기가
  실제로 잡는지 확인한 뒤 결과를 믿는다.

### 자리를 지정한 장식(absolute)은 z-index 없이도 그냥 글씨 위에 칠해진다
- 증상: 드래프트 히어로 아래 배지("이 형질을 얻으면 · 매의 눈")를 오라 장식(`.draft-aura`)이 덮어
  글씨가 뭉갰다. DOM 에서 배지가 오라보다 **뒤에** 있는데도 그랬다.
- 원인: z-index 문제가 아니라 **칠하는 순서**다. 같은 쌓임 맥락에서 브라우저는 배경 → 블록 → 부동 →
  인라인 → **자리를 지정한 요소(positioned)** 순으로 칠한다. 그래서 `position:absolute` 인 장식은
  `position:static` 인 형제보다 DOM 순서와 무관하게 늘 위에 온다. 게다가 오라는 담긴 칸(164px)보다
  큰 196px 원이라 아래로 16px 삐져나와 바로 밑 배지와 겹치는 자리에 있었다.
- 재발 방지책: 장식 위에 있어야 하는 글씨 요소에는 **자리를 지정**한다(`position:relative`).
  장식에는 `pointer-events:none` 을 함께 줘 탭도 안 먹게 한다. 일반화: "DOM 에서 뒤에 있으니 위에
  그려지겠지"는 **자리를 지정한 형제가 하나라도 있으면 틀린다.**

### 임시 worktree 에 node_modules 를 junction 으로 걸지 말 것 (원본이 지워진다)
- 증상: 검증용 임시 git worktree 를 정리하다 `git worktree remove --force` 가 **원본 저장소의
  `node_modules/.bin` 을 지웠다.** tsc 가 실행 불가가 되어 `npm install` 로 복구했다.
- 원인: worktree 안의 `node_modules` 를 원본으로 향하는 junction(윈도우 심볼릭 링크)으로 만들어 뒀다.
  삭제가 링크를 **따라 들어가** 원본 파일을 지웠다.
- 재발 방지책: 임시 worktree 에는 node_modules 를 링크하지 말고 복사하거나 `NODE_PATH` 로 가리킨다.
  애초에 **같은 트리에서 다른 세션이 저장할 때마다 dev 서버가 리로드되는 것**을 피하려던 것이었으니,
  그럴 땐 worktree 대신 자기 포트로 서버를 따로 띄우는 쪽이 싸다.

### 겹침 검사기가 DOM 만 재서 "패널이 캔버스 글씨를 가리는 것"을 세 번 놓쳤다
- 증상: 왼쪽 위 목표 줄(DOM)이 두 줄로 늘거나 상세를 펼치면, 그 뒤의 **빨간 보스 등장 문구·초록
  통과 문구·위협 예고 전광판**(전부 Pixi 캔버스)이 가려져 안 읽혔다. 사용자가 세 번 지적했고
  (2026-08-05: "빨간 글씨, 초록 글씨들이 가려서 안 보이는 문제도 있고") 그동안 `npm run overlap` 은
  내내 초록불이었다. 같은 날 런 종료 진척도 화면은 위(제목 "이번 혈통이 남긴 자취")가 잘려 있었다.
- 원인 (셋):
  ① **검사기가 DOM 만 쟀다.** 한계로 주석에 적어 두기만 하고("Pixi 를 옮겼으면 스크린샷도 볼 것")
     실제로는 아무도 안 봤다. 적어 둔 한계는 방지책이 아니다.
  ② **Pixi 쪽이 DOM 높이를 고정값으로 알고 있었다.** highlights 는 "goalBar 는 두 줄 ≈ 60px" 이라
     보고 y=66 을 박아 뒀는데, 그 줄은 문구에 따라 자란다(보스 판 74px · 상세 펼치면 251px 실측).
     자라는 것을 상수로 아는 순간 언제나 틀린다.
  ③ 검사 장면에 **"그 순간에만 뜨는 화면"이 하나도 없었다.** 위협 예고·판정 플래시·보스 등장·런 종료
     진척도는 잠깐만 떠서, 13개 장면 어디에도 안 잡혔다.
- 해결:
  · goalBar 가 자기 아래 끝을 실측해 내놓고(`bottomPx`, ResizeObserver) main 이 그 값을 Pixi 위젯에
    넘긴다 → 위에서부터 **HUD → 플래시 → 전광판** 순으로 쌓인다(전광판은 화면 밖으로 나가지 않게 클램프).
    자리를 옮기지 않고 "차지한 높이를 알려 주는" 쪽을 고른 이유: 위협 예고는 "왜 졌는지 모르는데 졌다"를
    막는 핵심 안내라 화면 한복판을 지켜야 하고, HUD 는 앞으로도 문구에 따라 계속 자란다.
  · 그리는 쪽이 자기 글씨의 화면 좌표를 `body.dataset.pixiText` 로 내보내고(`src/render/pixiTextRects.ts`)
    검사기가 그 사각형에 점을 찍어 **맨 위가 캔버스인지** 히트 테스트한다(⑤ 캔버스 가림).
    투명한 레이아웃 상자는 안 센다(실제로 칠하는 배경·backdrop-filter·자기 글자가 있을 때만) ·
    전체 화면 오버레이가 덮는 것은 정상이라 넘긴다 · 세로 표본에 가장자리(6%·94%)를 넣어 "윗줄만
    8px 잘리는" 얇은 띠까지 잡는다.
  · `?ovhook` 개발 전용 문으로 검사기가 그 순간들을 만든다(진짜 보스 소환·진짜 해금표 · 가짜 문구 금지).
  · 세로로 자라는 전체화면은 `overflow-y:auto` + **가운데 정렬을 auto 마진으로**. flex 의
    `justify-content:center` 는 넘칠 때 시작 모서리를 안 지켜 위가 잘린다(런 종료 진척도·세부 종 선택).
- 재발 방지책:
  · **DOM 과 캔버스가 같은 화면을 나눠 쓰면, 한쪽이 차지한 자리를 다른 쪽에 값으로 넘겨라.** 상수로
    적어 두면 반드시 어긋난다.
  · **검사기에 "그 순간에만 뜨는 화면"을 반드시 넣어라.** 상시 화면만 재는 검사기는 상시 화면만 지킨다.
  · **한계를 주석에 적는 것으로 끝내지 마라.** 적힌 한계는 세 번 다 안 읽혔다. 잴 수 없으면 잴 수
    있게 만드는 것(좌표를 내보내는 배관)이 답이다.
  · 새 검사 항목을 넣으면 **수정 전 코드로 되돌려 빨간불이 실제로 뜨는지 확인**한다(이번엔 5개 장면
    7건이 떴다). 안 뜨면 검사기가 아직 부족한 것이다.

## 내가 쓴 주석을 사용자 지시로 착각해 근거로 인용한다 (2026-08-06 발견 · 프로세스 실수)

- 증상: 회의 중에 `config.ts:38-42`(단계 경험치 상한의 근거)와 `genome.ts:94-97`(무리 성향을 능력

  · **주석을 근거로 인용할 때 말로 구분한다.** "이건 사용자가 정한 것" / "이건 내가 전에 판단한 것".
  · **내 판단을 인용할 때는 전제가 아직 유효한지 함께 따진다.** 특히 게임 방향이 크게 바뀐 뒤
    (관전 → 조종 전환 같은) 그 이전에 쓴 주석은 전부 의심 대상이다.
  · 일괄 치환은 하지 않는다. 기존 "사용자 지시/지적/요청/방향" 95곳이 진짜 사용자 발화인지

## GitHub Pages 배포가 `deployment_queued` 에서 10분 타임아웃으로 죽는다 (2026-08-06 재발)

- 증상: `build` 잡은 **성공**인데 `deploy` 잡만 실패한다. 로그가 `Current status: deployment_queued`
  를 5초 간격으로 되풀이하다 `Timeout reached, aborting!` 로 끝난다. 사이트는 **이전 번들을 계속
  서빙**한다(`curl` 로 `assets/index-*.js` 해시를 보면 안 바뀌어 있다).
- 원인: 우리 쪽 빌드가 아니라 **GitHub Pages 배포 큐**가 막힌 것이다. `gh run rerun --failed` 로
  세 번 재시도해도 같은 지점에서 죽었다.
- 확인 방법(빌드 문제와 가르는 법 · 이걸 먼저 하라):
  · `gh run view <id> --json jobs -q '.jobs[] | "\(.name): \(.conclusion)"'` → `build: success` 면 우리 잘못이 아니다.
  · `curl -s <사이트> | grep -o 'assets/index-[A-Za-z0-9_-]*\.js'` 로 실제 서빙 중인 번들 해시를 본다.
- 재발 방지책:
  · **세 번 넘게 재시도하지 마라.** 재시도마다 사용자에게 실패 메일이 간다(push 를 몰아 하는 이유와 같다).
    세 번 실패하면 GitHub 쪽 문제로 판단하고 **사용자에게 알린 뒤 멈춘다.**
  · 코드는 이미 `origin/main` 에 올라가 있으므로, **큐가 풀린 뒤 아무 커밋이나 하나 push 하면**
    그때 함께 배포된다. 급하면 Actions 탭에서 workflow 를 수동 실행(`workflow_dispatch`)한다.
